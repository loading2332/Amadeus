# Amadeus 全功能对齐 Akashic 按天推进总计划

> 这是一份“总路线图 + 每天最小闭环”的主计划，不是假装精确到 40 天后每个文件名的伪细案。原因很简单：`Amadeus` 已经不是空仓库，后续每个阶段都会改变代码边界。真正负责的做法是：
>
> 1. 先把完整迁移主线拆成按天推进的闭环。
> 2. 只把最近 1 个阶段写成可直接执行的细案。
> 3. 每进入下一个阶段前，再基于当时真实代码写该阶段的细案。
>
> 这份计划还有一个额外约束：**不走“先把 40 天最小实现全堆完，最后统一大重构”的路线。**
>
> 采用的策略是：
>
> 1. 每天只做一个最小闭环，保证你能跟上。
> 2. 每天闭环后做一次小收口，避免临时补丁留在主链。
> 3. 每个阶段最后一天固定做回归验证、边界硬化和代码精读。
> 4. 允许“能力少”，不允许“结构乱”。

## 0. 计划前提

### 这份计划里的“类似 Akashic”是什么意思

这里按 **能力链对齐** 定义目标，而不是按 **目录结构复制** 定义目标。

也就是说，Amadeus 的目标不是把 `../akashic-agent` 原样搬过来，而是把这些能力链补齐：

1. Prompt / Context
2. Session / History
3. Provider / Passive Runtime
4. Markdown Memory
5. Vector Memory / Retrieval
6. Tool Runtime
7. Passive Agent Loop
8. Lifecycle / Plugin System
9. Scheduler / Proactive / Drift
10. Observability / Dashboard / Eval

不默认照搬的内容：

- Akashic 的历史目录结构
- 未经验证的旧模块
- 为了兼容旧行为而存在的包袱

### 当前范围假设

默认先追求 **核心能力链完整对齐**，再按需要补外层 transport。

这意味着：

- 必做：tool loop、plugin、proactive、drift、observability、eval
- 后做：多渠道适配、UI 打磨、历史插件生态扩展

如果后续你明确要做 “Akashic 级别的 Telegram / QQ / dashboard transport 全对齐”，就在第 5 阶段后加 transport 扩展支线。

## 1. 当前阶段地图

### 现在已经实现了什么

从当前代码和测试看，`Amadeus` 已经有一条可运行主链：

```text
CLI chat
-> build_passive_app()
-> PassiveRuntime.run_turn()
-> ContextBuilder.render()
-> LLMProvider.chat()
-> parse_response()
-> SessionManager.save()
-> TurnCommitted
-> Markdown memory maintenance
-> vector ingest / retrieval
```

对应证据：

- `amadeus/bootstrap.py`
- `amadeus/runtime.py`
- `amadeus/memory.py`
- `amadeus/vector_memory.py`
- `tests/test_bootstrap.py`
- `tests/test_runtime.py`
- `tests/test_session_memory_runtime.py`
- `tests/test_vector_memory.py`

当前测试基线：

```powershell
New-Item -ItemType Directory -Force .pytest_tmp | Out-Null
$tmp = (Resolve-Path .pytest_tmp).Path
$env:TEMP = $tmp
$env:TMP = $tmp
uv run --extra dev pytest -q
```

当前结果：

```text
79 passed
```

### 主链路是什么

当前主链不是 agent loop，而是 **single-shot passive runtime**：

```text
user input
-> render prompt/context
-> call provider once
-> parse assistant text
-> persist user/assistant messages
-> emit TurnCommitted
-> refresh markdown memory
-> optional vector retrieval on next turn
```

### 哪些能力还是半成品

已经完成 v1，但还不是 Akashic 对齐：

- Vector memory 只完成了 retrieval evidence 链，尚未暴露成 tool / loop / forget runtime
- Runtime 还是 single-shot，不支持 tool call 多步循环
- 没有正式 Tool Runtime、Tool Registry、Hook Pipeline
- 没有 Lifecycle phases 和 Plugin System
- 没有 Scheduler / Proactive / Drift runtime
- 没有系统级 observability / dashboard / eval harness

### 下一个最值得做的最小闭环

**Day 1 不是直接写功能，而是先把验证基线收口。**

原因：

- 你现在的测试不是代码失败，而是默认临时目录权限失败。
- 如果不先把验证入口固定下来，后面每天都会重复踩“环境误报”。
- 工程上先修验证，再堆能力，比“边开发边赌环境”稳得多。

**Day 2 到 Day 7 才进入 Tool Runtime v1。**

原因：

- Tool Runtime 是 Passive Loop、Plugin、Proactive 的共同前置。
- 当前最卡主线的不是 retrieval，而是“没有统一工具抽象”。
- 直接跳去做 agent loop，会把工具定义、执行、安全、trace 混成一层。

### 这份计划允许什么样的“最小实现”

可以接受的简陋：

- 能力覆盖先只做核心路径
- 非核心 UX、配置便利性、可视化入口先轻量
- 某些阶段先只支持只读能力或单一 happy path

不可以接受的简陋：

- 用临时补丁代替长期边界
- 把 fake/stub/helper 混进生产主链
- 没有稳定 contract 就提前扩功能
- 用“先通过再说”的方式绕开测试和验证
- 明知接口命名、职责分层已经失真，还留到最后一起重构

换句话说，这份计划追求的是 **可继续长大的最小实现**，不是 **最省事的最小实现**。

## 2. 总体迁移顺序

按依赖关系，推荐总顺序是：

```text
已完成：
1. Prompt / Context
2. Session / History
3. Provider / Passive Runtime
4. Markdown Memory
5. Vector Memory / Retrieval v1

接下来：
6. Verification Baseline
7. Tool Runtime v1
8. Passive Agent Loop v1
9. Memory Tools / Retrieval Deepening
10. Lifecycle / Plugin Mini-Core
11. Scheduler / Outbound Ports
12. Proactive v1
13. Drift v1
14. Observability / Dashboard
15. Eval / Hardening / Gap Close
```

为什么这样排，而不是别的顺序：

- 不先稳住验证，后面所有“通过/失败”都不可信。
- 不先做 Tool Runtime，就没有干净的 tool loop 插入点。
- 不先做 Passive Loop，Plugin 插入点会反复变化。
- 不先做 Scheduler / Outbound，Proactive 只能停留在概念上。
- 不先做 Observability / Eval，后半程会越来越难定位问题。

## 4. 每天的统一执行模板

无论做到哪一天，都按这个节奏推进：

1. 先讲当天目标
2. 讲清这一天卡的真实工程问题
3. 先写或补当天的 focused test
4. 写最小实现，不顺手扩 scope
5. 做一次当天范围内的小收口
6. 跑 focused test + 主链回归
7. 做一次链路代码精读
8. 总结今天你应该学会什么

这里的“小收口”默认至少包含：

- 把临时命名收成正式命名
- 删除本次闭环里不再需要的重复分支
- 检查新增接口是否已经有清晰输入/输出/错误形状
- 确认测试测的是正式链路，不是临时绕路

目标不是当天就“做漂亮”，而是避免把明知错误的结构继续往后带。

## 5. 每个阶段的统一收口规则

每个阶段最后一天，不只是“跑一下测试”，而是固定做一次阶段硬化。默认包含：

1. 回归验证
2. 边界审计
3. 局部重构
4. 代码精读
5. 学习复盘

### 1. 回归验证

- 新增 focused test 全部通过
- 旧主链 smoke 仍然通过
- 至少验证一条真实 CLI/runtime 路径，而不只看单测

### 2. 边界审计

至少回答清楚：

- 这一阶段新增的核心 contract 是什么
- 哪个模块负责定义它，哪个模块负责消费它
- 有没有把本该在 composition/runtime 层的逻辑偷塞进工具、插件或 provider

### 3. 局部重构

只允许做服务于当前阶段的重构，不做无关大扫除。优先收：

- 重复的数据结构
- 漏斗式 if/else 分发
- 漂移的命名
- 不一致的 error/result shape

### 4. 代码精读

必须能按当前阶段的真实主链讲清：

- 输入从哪里进入
- 中间在哪些对象/函数之间流转
- 状态在哪里落盘或持久化
- 错误在哪里被拦截、转换或上抛

### 5. 学习复盘

阶段结束时至少沉淀这五样：

- 这一阶段最关键的 1-3 个文件
- 最重要的 contract/接口
- 最容易写错的边界
- 一条最有代表性的验证命令
- 如果你自己重做，第一步先看什么

## 6. 哪些债可以留到后面，哪些不能

可以延后：

- 非核心工具数量扩充
- CLI 交互细节打磨
- dashboard/TUI 的体验优化
- 更远阶段的泛化抽象

不能延后：

- 主链 contract 不稳定
- 错误形状在不同模块里各说各话
- 测试绕开真实执行链
- 临时 helper 已经承担正式职责
- 明知模块分层放错还继续叠功能

判断标准很简单：

- 如果它只影响“体验是否更完整”，可以后放。
- 如果它影响“后续阶段是不是要推翻今天的边界”，就必须当天或当阶段收掉。

## 7. 每天的统一验证模板

### 通用测试命令

```powershell
New-Item -ItemType Directory -Force .pytest_tmp | Out-Null
$tmp = (Resolve-Path .pytest_tmp).Path
$env:TEMP = $tmp
$env:TMP = $tmp
uv run --extra dev pytest -q
```

### 通用 CLI smoke

准备好 `.env` 后，用：

```powershell
uv run python -m amadeus chat "hello" --env .env --workspace-root .tmp_workspace --show-ids
```

正常结果：

- 终端打印 assistant 回复
- 同时打印 `session`、`user_message_id`、`assistant_message_id`
- `.tmp_workspace` 下出现 `sessions.db` 和 `memory/` 目录

异常含义：

- provider 配置报错：说明 `.env` 不完整
- 只有回复、没有持久化：说明 runtime 到 session/event 的链路断了
- memory 文件不刷新：说明 `TurnCommitted -> memory maintenance` 断了
