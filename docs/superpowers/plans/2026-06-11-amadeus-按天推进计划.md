# Amadeus 全功能对齐 Akashic Lesson 推进总计划

> 这是一份“总路线图 + Lesson 复现切片”的主计划，不是假装精确到 40 节课后每个文件名的伪细案。原因很简单：`Amadeus` 已经不是空仓库，后续每个阶段都会改变代码边界。真正负责的做法是：
>
> 1. 先把完整迁移主线拆成按 Lesson 推进的 Akashic 对齐复现切片。
> 2. 只把最近 1 个阶段写成可直接执行的教学 + 实现细案。
> 3. 每进入下一个阶段前，再基于当时真实代码写该阶段的细案。
>
> 这份计划还有一个额外约束：**不走“先把 40 节课简化实现全堆完，最后统一大重构”的路线。**
>
> 采用的策略是：
>
> 1. 每节课都先做 Akashic 源码课，再做 Amadeus 复现练手。
> 2. 每节课只复现一段 Akashic 真实设计，保证你能真正讲清。
> 3. 每节课后做一次复盘、eval/smoke 沉淀和 Akashic gap audit。
> 4. 允许“分步复现”，不允许“为了快而偏离 Akashic”。
>

## 0. 计划前提

### 这份计划里的“对齐 Akashic”是什么意思

这里按 **真实设计复现 + 能力链对齐** 定义目标，而不是按 **目录结构复制** 定义目标。

也就是说，Amadeus 的目标不是把 `../akashic-agent` 原样搬过来，也不是先做一个简化 agent。目标是通过亲手复现 Akashic 的核心设计来掌握它，再在掌握后的基础上做二开和简历项目包装。

每节课默认分成两部分：

1. Akashic 源码课：定位源码、调用链、关键类型、状态流、测试或验证方式，讲清设计动机和复杂点。
2. Amadeus 复现练手：在确认理解后，对照 Akashic 在 Amadeus 中复现对应设计，并补验证和复盘。

必须复现和掌握的核心能力链：

1. Prompt / Context
2. Session / History
3. Provider / Passive Runtime
4. Markdown Memory
5. Vector Memory / Retrieval
6. Tool Runtime
7. Passive Agent Loop
8. Lifecycle / Plugin System
9. Scheduler / Proactive / Drift
10. Observability / Dashboard / Eval

不默认照搬的内容：

- Akashic 的历史目录结构
- 未经验证的旧模块
- 为了兼容旧行为而存在的包袱

### 当前范围假设

默认先追求 **核心能力链真实复现与完整理解**，再按需要补外层 transport。

这意味着：

- 必做：tool loop、plugin、proactive、drift、observability、eval
- 后做：多渠道适配、UI 打磨、历史插件生态扩展

如果后续你明确要做 “Akashic 级别的 Telegram / QQ / dashboard transport 全对齐”，就在第 5 阶段后加 transport 扩展支线。

### Evaluation 贯穿策略

Evaluation 不是最后阶段才补的功能，而是每个阶段都要沉淀的行为级验证资产。

每节课至少回答：

1. 本课 Akashic 对应行为是什么。
2. Amadeus 复现后应该通过哪些 focused tests。
3. 哪些 smoke/eval case 可以长期保留，防止后续 loop、tool、memory、plugin、proactive 行为漂移。

后期的 eval harness / dashboard 负责统一运行和展示这些 case；前期每节课就要开始积累 case。

### Akashic 关键机制覆盖矩阵

本计划必须和 `docs/superpowers/plans/2026-06-18-akashic-关键机制覆盖矩阵.md` 配套使用。

40 节课编号不变，但每节课进入前必须对照覆盖矩阵回答：

1. 本课覆盖哪些 Akashic 关键机制。
2. 本课明确不覆盖哪些关键机制。
3. 不覆盖项是否仍属于必须复现。
4. 如果必须复现，排到哪一课补。
5. 本课沉淀什么 focused test / smoke / eval seed。

如果某节课只写了模块标题，没有覆盖矩阵和 gap audit，就不能算课程设计完成。

## 1. 当前阶段地图

### 现在已经实现了什么

从当前代码和测试看，`Amadeus` 已经有一条可运行主链，并且已经进入被动多步 tool loop 的基础实现阶段：

```text
CLI chat
-> build_passive_app()
-> PassiveRuntime.run_turn()
-> ContextBuilder.render()
-> LLMProvider.chat()
-> parse_response()
-> SessionManager.save()
-> TurnCommitted
-> Markdown memory maintenance
-> vector ingest / retrieval
```

对应证据：

- `amadeus/bootstrap.py`
- `amadeus/runtime.py`
- `amadeus/memory.py`
- `amadeus/vector_memory.py`
- `tests/test_bootstrap.py`
- `tests/test_runtime.py`
- `tests/test_session_memory_runtime.py`
- `tests/test_vector_memory.py`

当前测试基线：


当前结果：

```text

```

### 主链路是什么

当前主链已经不是纯 single-shot passive runtime，而是：

```text
user input
-> render prompt/context
-> provider.chat()
-> response.tool_calls ?
   -> append assistant(tool_calls)
   -> execute tools
   -> append tool(result)
   -> provider.chat() again
-> final assistant reply
-> persist user / assistant
-> emit TurnCommitted
-> refresh markdown memory
-> optional vector retrieval on next turn
```

也就是说，当前系统已经有 **基础多步 tool loop**，但还没有完全收口成 Akashic `Reasoner.run()` 的完整语义。

### 哪些能力还是半成品

已经具备部分能力，但还需要继续做 Akashic 对齐复现：

- Vector memory 只完成了 retrieval evidence 链，尚未暴露成 tool / loop / forget runtime
- Runtime 已经有基础多步 tool loop、iteration limit summary、tool_chain 持久化和 history 过滤，但尚未完整复现 Akashic 的 passive reasoner 语义收口
- Tool Runtime 已经具备 Registry / Executor / Hook Pipeline 基础，还需要继续对照 Akashic 做更完整的 request/result/trace 语义以及 lifecycle 接入
- 没有 Lifecycle phases 和 Plugin System
- 没有 Scheduler / Proactive / Drift runtime
- 没有系统级 observability / dashboard / eval harness，但每课都要开始沉淀 eval/smoke case

### 下一个最值得做的 Akashic 对齐复现切片

**当前最值得做的不是回到 Lesson 1，而是从当前真实阶段继续做 Lesson 10 的 teach 化和 Akashic 对齐收口。**

原因：

- Tool Runtime 和基础多步 loop 已经落地，继续假装“还没进入 loop”会让课程起点失真。
- 当前最大的风险不是“不会跑”，而是“已经能跑，但主链语义和 Akashic 还没讲清、没收口”。
- 因此应该直接进入：
  - Lesson 10 Part 1：Akashic Passive Reasoner 多步 loop 源码课
  - Lesson 10 Part 2：Amadeus 当前 loop 对照精读与 gap 标注
  - Lesson 11：tool message 持久化边界与 session history 边界

### 这份计划允许什么样的“分步复现”

可以接受：

- 一节课只复现 Akashic 真实设计中的一段
- 非核心 UX、配置便利性、可视化入口先轻量
- 某些阶段先复现 Akashic 机制中的基础路径，再在同一机制下继续补齐

不可以接受：

- 用临时补丁代替长期边界
- 把 fake/stub/helper 混进生产主链
- 没有稳定 contract 就提前扩功能
- 用“先通过再说”的方式绕开测试和验证
- 明知接口命名、职责分层已经失真，还留到最后一起重构
- 因为 Akashic 复杂就改写成 Amadeus 自己的简化替代

换句话说，这份计划追求的是 **Akashic 对齐的分步复现**，不是 **能跑就行的临时简化版本**。

## 2. 总体迁移顺序

按依赖关系，推荐总顺序是：

```text
已完成：
1. Prompt / Context
2. Session / History
3. Provider / Passive Runtime
4. Markdown Memory
5. Vector Memory / Retrieval

接下来：
6. Verification Baseline
7. Tool Runtime
8. Passive Agent Loop
9. Memory Tools / Retrieval Deepening
10. Lifecycle / Plugin Mini-Core
11. Scheduler / Outbound Ports
12. Proactive
13. Drift
14. Observability / Dashboard
15. Eval / Hardening / Gap Close
```

为什么这样排，而不是别的顺序：

- 不先稳住验证，后面所有“通过/失败”都不可信。
- 不先做 Tool Runtime，就没有干净的 tool loop 插入点。
- 不先做 Passive Loop，Plugin 插入点会反复变化。
- 不先做 Scheduler / Outbound，Proactive 只能停留在概念上。
- 不先做 Observability / Eval，后半程会越来越难定位问题。

## 5. 每个阶段的统一收口规则

每个阶段最后一课，不只是“跑一下测试”，而是固定做一次阶段硬化。默认包含：

1. 回归验证

3. 边界审计
4. 局部重构
5. 代码精读
6. 学习复盘
7. 简历叙事沉淀

### 1. 回归验证

- 新增 focused test 全部通过
- 旧主链 smoke 仍然通过
- 至少验证一条真实 CLI/runtime 路径，而不只看单测

### 2. Akashic gap audit

至少回答清楚：

- 本阶段精读了 Akashic 哪些源码文件和测试
- Amadeus 已经复现了 Akashic 的哪些接口、数据流、生命周期边界和验证思想
- 哪些 Akashic 能力还没复现，但属于同一机制后续必须补齐
- 有没有任何 Amadeus 自己发明的简化替代；如果有，必须说明是否需要回收

### 3. 边界审计

至少回答清楚：

- 这一阶段新增的核心 contract 是什么
- 哪个模块负责定义它，哪个模块负责消费它
- 有没有把本该在 composition/runtime 层的逻辑偷塞进工具、插件或 provider

### 4. 局部重构

只允许做服务于当前阶段的重构，不做无关大扫除。优先收：

- 重复的数据结构
- 漏斗式 if/else 分发
- 漂移的命名
- 不一致的 error/result shape

### 5. 代码精读

必须能按当前阶段的真实主链讲清：

- 输入从哪里进入
- 中间在哪些对象/函数之间流转
- 状态在哪里落盘或持久化
- 错误在哪里被拦截、转换或上抛

### 6. 学习复盘

阶段结束时至少沉淀这五样：

- 这一阶段最关键的 1-3 个文件
- 最重要的 contract/接口
- 最容易写错的边界
- 一条最有代表性的验证命令
- 如果你自己重做，第一步先看什么

### 7. 简历叙事沉淀

- 这个模块解决什么工程问题

## 6. 哪些债可以留到后面，哪些不能

可以延后：

- 非核心工具数量扩充
- CLI 交互细节打磨
- dashboard/TUI 的体验优化
- 更远阶段的泛化抽象

不能延后：

- 主链 contract 不稳定
- 错误形状在不同模块里各说各话
- 测试绕开真实执行链
- 临时 helper 已经承担正式职责
- 明知模块分层放错还继续叠功能

判断标准很简单：

- 如果它只影响“体验是否更完整”，可以后放。
- 如果它影响“后续阶段是不是要推翻本课边界”，就必须本课或当阶段收掉。
