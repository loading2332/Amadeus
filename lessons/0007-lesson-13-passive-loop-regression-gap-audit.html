Part 1：Akashic 源码课

Akashic 这阶段不是一个函数能讲完，而是三层配合：Reasoner 主控 loop，Session/History 持久化事实，AfterTurn 把结果变成可观测事件。

1. Reasoner 拥有主控权

../akashic-agent/agent/core/passive_turn.py 里的 DefaultReasoner.run_turn() 控制 provider 调用、tool 执行、tool result 回灌、max iteration 和 context retry。

2. tool_chain 是事实压缩层

Akashic 不把 tool messages 当普通聊天内容长期堆在 history 里，而是把执行事实压到 assistant message 的 tool_chain，未来再重建给模型。

3. Context retry 是 turn 内应急

DEFAULT_CONTEXT_TRIM_PLANS 决定先删哪些 prompt block，再缩 history window；这是 fallback，不是长期 compact。

4. AfterTurn 是收口层

agent/lifecycle/phases/after_turn.py 会构造 TurnCommitted，把 tool_chain、预算、react stats 等事实交给后续观察和后台处理。

人话版：Akashic 的被动 loop 不是“问一次模型，跑一次工具”。它是一个 turn 生命周期：模型请求、工具执行、消息回灌、重试降载、事实提交、后置处理，每一步都有边界。

Akashic 主链缩略图

Passive turn
  -> DefaultReasoner.run_turn(...)
       -> render prompt + history window
       -> provider.chat(...)
       -> if tool_calls:
            assistant(tool_calls) -> tool(result) -> provider.chat(...)
       -> if ContextLengthError:
            next trim plan -> render again -> retry
       -> if max_iterations:
            return staged summary, not crash
  -> persist assistant message with tool_chain / context_retry
  -> after_turn phase builds TurnCommitted
  -> observe / memory / background workers consume committed facts

Part 2：Amadeus 当前对照

Amadeus 已经不是 single-shot runtime。当前主链可以概括为：

PassiveRuntime.run_turn(...)
  -> session.get_history()
  -> build_context_trim_attempts(...)
  -> ContextBuilder.render(RuntimeContext)
  -> Provider.chat(messages, tools)
  -> _ToolLoopReasoner.run(...)
       -> execute tools
       -> append assistant(tool_calls)
       -> append tool(result)
       -> call provider again
  -> persist assistant message extra.tool_chain / extra.context_retry
  -> append Event(..., extra={tool_chain, context_retry})

Akashic Gap Audit

这里不要把“能跑”误判成“完整复现”。按三类审计：

可作为主链 Green

  • provider 和 loop 编排层已经解耦。
  • 多步 tool loop 已经进入正式 runtime。
  • tool_chain 持久化和 history 重建已经有测试。
  • context fallback 已经覆盖成功 retry 和全失败路径。
  • max_iterations 返回阶段性总结，而不是未闭合错误。

下一阶段前要补强 Yellow

  • prompt block 渲染时目前是先 render 再过滤，Akashic 更接近禁用块不参与构建。
  • runtime_metadata 需要拆成更明确的上下文注入和系统元数据。
  • fallback 次数还没有形成长期统计，无法识别长期 block fallback。
  • Event 只是轻量日志，还不是 Akashic 的 TurnCommitted 生命周期事件。

不能假装已完成 Red

  • 完整 lifecycle phase pipeline 还没有迁移。
  • observe writer / dashboard 级预算查询还没有。
  • tool discovery / preloaded tools / skill catalog 体系还没有。
  • memory post-response worker 还没有接到 committed turn。

常见误区

误区 1：测试过就等于完整复现

不对。测试证明当前主链行为稳定，不证明 Akashic 的 lifecycle、observe、tool discovery 都复现了。

误区 2：Event extra 就是 TurnCommitted

不对。Amadeus 现在只是轻量事件记录；Akashic 的 committed event 是生命周期边界和后台处理入口。

误区 3：runtime_metadata 可以一直混用

不能。短期可用，长期会让 LLM-visible prompt、system metadata、outbound metadata 混在一起。

误区 4：Lesson 13 应该继续加功能

这节的价值是收口。不做 gap audit，后面 memory tool 会接到不稳定边界上。

简历可讲述版本

我在 Amadeus 中复现了 Akashic 被动 Agent Loop 的核心主链：provider 只负责 LLM API 和错误归一， runtime 持有多步 tool loop 与 context-length fallback，session 通过 assistant message 的 tool_chain 持久化工具执行事实，并在后续 history 中重建模型协议消息。阶段验收通过 focused 回归和全量测试， 同时明确保留了 lifecycle event、预算观测、tool discovery 等与 Akashic 的差距，作为后续迁移边界。
