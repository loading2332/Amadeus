本课卡点

memory_engine.query() 已经能预注入 context，为什么还要做 recall_memory tool？答案是：控制权从应用前置检索，转到模型按需检索。

Memory Tools / Retrieval Deepening

从“自动塞记忆”到“模型主动召回”

Lesson 14 的任务不是再做一个检索函数，而是复现 Akashic 的边界：retrieval 既可以作为 runtime 的 context 预注入， 也可以作为 LLM 可调用的 recall_memory 工具进入 tool loop。后者会产生 tool_call、tool_result、tool_chain 和可审计 evidence。

与 MISSION.md 的关系

为什么这节重要

复杂 agent 不只是“有记忆”，还要能决定什么时候查记忆、查什么、查到后如何引用证据。这个能力会直接进入简历项目叙事。

外部协议参考：为什么它是 tool，而不是普通函数

        

          OpenAI 的 function calling 文档把通用模式讲得很清楚：模型根据工具 schema 生成函数调用参数，应用代码执行函数，再把结果回传给模型继续生成答案。

          RESOURCES.md
        

        

          人话版：recall_memory 必须是 tool，因为“要不要查、用什么 query 查、查几条、按什么意图查”应该由模型在推理过程中决定，而不是每轮 runtime 都提前替它查完。
        

      


      

        
两条 retrieval 链路不要混

        

          
          
          
        

        

          
runtime.run_turn(...)
  -> memory_engine.query(MemoryQuery(text=user_message))
  -> render_context_block(...)
  -> retrieved_memory prompt block
  -> provider.chat(messages)

          
这是 Amadeus 当前已有的能力：应用在模型调用前自动查一点记忆，作为 context block 塞给 LLM。

        

        

          
LLM sees tool schema
  -> LLM emits tool_call: recall_memory(...)
  -> runtime executes tool
  -> tool result appended to messages
  -> LLM uses result to answer
  -> tool_chain persists execution facts

          
这是 Lesson 14 要复现的能力：模型在推理中主动查记忆，结果进入 tool loop 和 tool_chain。

        

        

          
两条链解决的问题不同。Pre-retrieval 是“默认给模型一点可能相关的背景”；tool retrieval 是“模型发现缺事实时主动查，并留下可审计调用链”。后者更适合回答历史事实、偏好、做过什么、证据引用。

源码精读：先抓 4 个点

        

          1. description / parameters 不写死在工具类里
          
RecallMemoryTool.__init__() 接收 MemoryToolSpec，把 description 和 parameters 从 memory engine profile 注入。这说明 Akashic 不把工具描述当静态常量，而是让 memory engine 决定工具能力怎么暴露。

        

        

          2. execute() 的核心职责是把 tool args 转成 MemoryQuery
          
query、intent、memory_kind、time_filter、limit、channel/chat_id 都会被规整进 MemoryQuery、MemoryScope 和 MemoryQueryFilters。工具层不直接碰底层 store。

        

        

          3. 输出不是一段自然语言，而是结构化 JSON
          
_render_records() 返回 count、items、trace、citation_required、cited_item_ids。这让 LLM 能继续推理，也让系统能审计。

        

        

          4. evidence 是后续 fetch_messages 的桥
          
_render_evidence() 会保留 kind、refs、resolver、source_ref、metadata。Lesson 15 会继续讲为什么 recall 结果不是最终证据，必要时还要回源。

        

      


      

        
Akashic 测试告诉我们什么

        

          

            空 query / 空结果
            
空输入不应炸掉；返回 count=0 的结构化结果。

          

          

            intent / time_filter
            
不同意图会影响检索路径；时间过滤要能解析 today、recent_Nd、日期范围。

          

          

            fallback
            
embedding 失败或超时不能让工具整体不可用；可以退到 keyword 路径。

          

          

            evidence 保留
            
返回项要带 source_ref/evidence，方便后续 fetch_messages 回源。

          

          

            citation rule
            
使用记忆时必须留下引用标记，避免“像事实但没证据”。

          

          

            profile backed
            
工具描述来自 profile，不应在 tool class 中硬编码成永久规则。

          

        

      


      

        
常见误区

        
    
          
  • 误区：已有 memory_engine.query()，所以不需要 recall tool。纠正：一个是 runtime 预注入，一个是模型主动调用。
    • 
          
  • 误区：recall tool 直接返回自然语言就行。纠正：Akashic 返回结构化 JSON，保留 trace、evidence 和 citation rule。
    • 
          
  • 误区：tool 层可以直接查数据库。纠正：tool 应该依赖 memory API/facade，不应该越过 retrieval 抽象。
    • 
          
  • 误区：source_ref 就是最终答案证据。纠正：source_ref 是回源桥，Lesson 15 会接 fetch_messages。
