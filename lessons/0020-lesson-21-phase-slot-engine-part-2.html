寓言：Hotel Azure 那个没有编号的夜班

1. 新白板没有告诉任何人“你是第几步”

Hotel Azure 已经把老蔡的施工白板换成了一面空墙。今晚是第一次真正使用它。墙上没有 1、2、3，也没有 2.5；只有五张酒店自己的工牌，和一只刚送到的银色工具箱。

五张工牌分别属于领房卡的人、整理客房档案的人、填写交接单的人、召集夜班广播的人和最终签字的人。每张工牌背面都写着“我等谁完成”“我需要从推车里拿什么”“我会留下什么”。工具箱来自一家外部安防公司，酒店没人知道它应该排第几。

安防工程师没有去找值班经理申请一个数字。他只在工具箱上贴了一张纸：“等交接单填写完；推车里要有一份可修改的交接单；检查完成后，仍把这份交接单放回去。”

2. 外来工具箱先被登记，却没有立刻放上推车

仓库管理员先检查工具箱来自哪个供应商，把它记在供应商名下，然后打开箱盖确认里面确实是一件可执行的工具。登记时，工具箱仍属于安防公司；如果公司在开工仪式前撤单，管理员就能按供应商找到并移走它，不会把一个失去主人的工具留在夜班现场。

安防公司还要完成一次通电自检。管理员先抄下工具箱的工作说明，但没有马上宣布它已进入夜班。只有自检成功，说明才会正式进入“今晚可用”的清单。若自检失败，刚才登记的箱子、说明和供应商记录会一起清除。

3. 值班经理没有在原来的五人之间塞进第六个人

自检通过后，值班经理拿到一份“今晚所有外部工具”的快照。他没有逐张修改酒店工牌，也没有让安防工程师认识酒店的每位员工。他把五张内部工牌和工具箱说明一起交给排班员。

排班员先检查名字有没有重复，再把“等某张工牌完成”画成箭头。推车里的房卡、档案和交接单则被记在另一栏：它们证明交接材料是否闭合，却不会自己画出人员之间的箭头。

当两张卡同时可以执行时，排班员按固定规则取卡。因此同一批工牌每晚都会得到相同顺序。安防工具箱等“填写交接单”完成，所以自然出现在它之后；而夜班广播还没开始，工具箱便有机会先把安防提示写进交接单。

4. 真正的风险不是“排错一次”，而是换表换到一半

第二家供应商带来一个同名工具箱。排班员发现名字冲突，拒绝生成新排班表。值班经理没有把已经运行的旧表拆掉：他先在旁边完整生成候选表，确认可用后才会整体换上。候选表失败，墙上仍是原来的五张酒店工牌，夜班可以继续。

凌晨收工时，管理员先逐家通知供应商结束工作，随后从夜班表里撤走所有外部工具说明，最后才锁上存放客房记录的仓库。这样，工具箱不会在供应商已经离场后继续出现在下一次排班里，也不会在仓库先锁门后才尝试清理自己的状态。

5. 第二天，工程师发现“排班表”其实不是业务代码

新工程师问：“我们是不是专门为安防公司重写了一套夜班？”老蔡摇头。酒店只把原来那段不可拆的夜班流程，切成了五个各自有合同的小任务；安防公司贡献的是同一种小任务。排班规则根本不知道谁是安防公司，它只认识名字、依赖和产出。

直到这时，老蔡才翻开墙边的施工说明：那辆推车叫 BeforeTurnFrame；五张酒店工牌叫 built-in modules；外来工具箱叫 plugin module；排班员调用 topo_sort_modules()；整张可执行夜班表叫 Phase；值班经理在启动时完成的整体换表叫 phase rebuild。

你现在才看到本次复现真正做了什么：不是把一个插件回调塞进旧链，而是让宿主和插件提交同一种合同，再由一个通用执行引擎组装它们。

一句话定义
Amadeus 的 Phase Slot Engine 是一个共享 frame 的异步 module 链：组装函数合并 built-in 与 plugin modules，依据 module slot 做拓扑排序，依据 data slot 检查数据合同，Phase 再按既定顺序执行并要求最终 output。

为什么现在先做 before_turn？
它已经拥有 Session、Memory、Context 和 EventBus 的真实输入输出，可以证明 phase 不是孤立算法。先跑通一个垂直切片，再把同一引擎迁移到其他阶段，能把“机制正确”与“覆盖面完整”分开验证。

本课目标与 MISSION.md 的关系

MISSION.md 要求从真实设计来源、状态流和验证闭环掌握复杂 agent 系统。本课不是“写一个拓扑排序练习”，而是完成 Akashic → Amadeus 的判断式迁移：

  • 迁移通用接口：Frame、Module、Phase、slot 合同与拓扑关系。
  • 迁移生命周期：插件声明、Manager 持有、bootstrap 注入、runtime 执行、close 清理。
  • 保留 Amadeus 现有 Context、Session、Memory 和 EventBus 类型，不照搬 Akashic 目录结构。
  • 用真实 workspace plugin 改变 provider prompt，不把 fake 扩散进生产架构。

做完应看到：插件无需修改 PassiveRuntime.run_turn()，只声明一个 module，便可稳定落在 build_ctx 与 emit 之间；非法图在应用启动阶段失败并回滚。

Part 1：Akashic 源码课回顾

Part 1 已经确认四条核心事实：

  1. 拓扑排序发生在 default_*_modules() 组装函数，不发生在 Phase.__init__()。
  2. module slot 建图；data slot 只检查闭合，不会自动推断 producer 或决定顺序。
  3. consumer 若要稳定排在 producer 后，应同时依赖 producer 的 module slot 和所需 data slot。
  4. 缺失 plugin module 依赖会递归禁用；缺失 data slot 只 warning；重复 slot、环、执行异常、无 output 各有独立失败语义。

参考入口：Akashic phase.py、before_turn.py、plugin base、plugin manager。

通用 Phase engine：小接口，强合同

源码：amadeus/phase.py。

@dataclass
class PhaseFrame(Generic[InputT, OutputT]):
    input: InputT
    slots: dict[str, Any] = field(default_factory=dict)
    output: OutputT | None = None

class PhaseModule(Protocol[FrameT]):
    async def run(self, frame: FrameT) -> FrameT: ...

class Phase:
    async def run(self, input):
        frame = self._frame_factory(input)
        for module in self._modules:
            frame = await module.run(frame)
        if frame.output is None:
            raise RuntimeError("Phase 模块链未产生 output")
        return frame.output
对象输入输出/状态不负责什么
PhaseFrame本次调用的 input共享 slots 与最终 output不跨 turn 保存全局状态
PhaseModule具体 Frame读取/修改后返回 Frame不决定全图顺序
topo_sort_modulesbuilt-in + plugin modules确定性有序列表不执行 module
Phase已经排好序的 modules验证、执行并返回 output构造函数不做拓扑排序

零入度 tie-break

queue.sort(key=lambda item: (_is_builtin_slot(item), slot_order[item]))

同为零入度时 plugin slot 先于 built-in slot；同类保持注册顺序。这是 Amadeus 已用独立测试锁定的行为。注意：依赖边仍拥有更高约束力，tie-break 只处理图没有规定先后的节点。

inspect_phase() 会输出执行顺序、依赖树和数据合同。它是诊断入口，不改变图。

BeforeTurnInput 保留旧 runtime 的 session_key、user_message、retrieved_memory、active_skills 和 runtime_metadata。_PrepareContextModule 仍然读取真实 session history，并对 memory query 保持原有 fail-open 行为。因此这次重构改变的是编排方式，不改变上层调用接口和业务语义。

和 Akashic 的明确差异
Akashic 当前示例有六个 module，包含 before_turn.collect_exports；Amadeus 本切片只有五个。这里不是“等价完成”，而是有意保留到 Lesson 23 的 Gap，不能在讲述时把 collector 算作已实现。

真实 workspace plugin：不是测试里直接塞 module

fixture：prompt_marker/plugin.py。

class PromptMarkerModule:
    slot = "prompt_marker.before_turn"
    requires = ("before_turn.build_ctx", "session:ctx")
    produces = ("session:ctx",)

    async def run(self, frame: BeforeTurnFrame) -> BeforeTurnFrame:
        context = cast(BeforeTurnContext, frame.slots["session:ctx"])
        context.runtime_metadata["plugin_marker"] = "loaded through PassiveApp.start"
        return frame

class PromptMarker(Plugin):
    def before_turn_modules(self) -> list[object]:
        return [PromptMarkerModule()]

它同时依赖 before_turn.build_ctx 和 session:ctx：前者把 module 放到 build 后面，后者检查运行时数据合同。由于 plugin 与 before_turn.emit 在 build 完成后同时变为零入度，plugin-first tie-break 让 marker 先写入 context，emit 再把 context 交给已有 lifecycle handlers。

PluginManager 在 phase_modules stage 要求接口返回 list，但只在 initialize() 成功后，才把 tuple 提交到对应 import_path 名下。初始化失败不会泄漏 module；terminate/cleanup 会按 owner 删除它。

Runtime 与 App：为什么要原子重建

源码：runtime.py、bootstrap.py。

def set_before_turn_plugin_modules(self, modules: list[object]) -> None:
    candidate_modules = list(modules)
    candidate_phase = self._build_before_turn_phase(candidate_modules)
    self._before_turn_plugin_modules = candidate_modules
    self._before_turn = candidate_phase

顺序不能倒过来。构造候选 phase 时可能发现重复 slot 或循环依赖；只有候选完整成功，runtime 才同时替换 module 快照和 phase。这样失败不会留下“modules 已换、phase 还是旧的”半提交状态。

report = await plugin_manager.load_all()
runtime.set_before_turn_plugin_modules(plugin_manager.before_turn_modules)
# 成功后才把 App 标记为 STARTED

PassiveApp.start() 把插件加载与 phase 注入视为同一个启动事务。注入失败会恢复纯 built-in phase、终止已加载插件并保持 NEW，允许修正后重试。aclose() 则先 terminate plugins，再恢复纯 built-in phase，最后关闭 session store。

Tradeoff
当前做法每次插件集合变化都重建整条 before_turn phase，代价是 O(modules + edges)；换来的是不可变式快照、简单回滚和稳定诊断。当前模块规模很小，这比原地增删图节点更可维护。若未来需要运行时高频热插拔，才值得引入版本化快照或读写锁。

四类失败边界：什么时候警告，什么时候中断

情况当前行为原因
plugin module 缺失 module 依赖warning；递归禁用该 module 及依赖它的 plugin modules可选扩展缺失不应拖垮 built-in 主链
data slot 未闭合warning；不推断 producer、不自动排序、不禁用data contract 与执行图是两套信息
缺少 slot、重复 slot、循环依赖组装期抛 RuntimeError图身份或顺序无解，不能带病启动
module.run 抛异常原样向上传播引擎不应吞掉业务失败
链结束仍无 output执行期抛 RuntimeError“所有 module 都跑过”不等于 phase 完成

边界提醒：当前递归禁用只针对 plugin slot；built-in 合同破损会保留并告警，随后通常在执行时暴露。这保护可选插件，同时不把核心链错误伪装成“自动跳过”。

常见误区与排错顺序

  1. “写了 data slot 就会自动排序。”先检查 consumer 是否也声明 producer module slot。
  2. “priority 已经完全没用了。”依赖图解决有约束节点；tie-break 仍需一个确定规则处理无边节点，只是它不再承担业务依赖。
  3. “插件加载成功，所以 module 一定在执行。”沿 Manager property → App.start → runtime snapshot → inspect_phase 逐层检查。
  4. “Phase.__init__ 会帮我排序。”查看 default_before_turn_modules() 是否调用了 topo sort；Phase 只接收有序列表。
  5. “warning 就代表 engine 会修复合同。”data warning 只暴露风险，不推断、不补边；运行时仍可能 KeyError。
  6. “插件 module 应直接改 PluginManager 或 Runtime。”它只改 frame；宿主负责生命周期和注入，避免扩展反向控制容器。
资深工程师先看什么信号？
先打印 phase 顺序与 contracts，再看 Manager 快照所有权，最后才进 module.run 调试业务值。图没组对时，在 run 内加日志只会观察到错误结果的后半段。
