对应总计划 Lesson 11 Part 1

Tool Message 持久化边界与 Session History 边界

这一课回答一个非常容易想当然的问题：为什么 tool 中间消息明明参与了 loop，却不应该被当成普通聊天历史直接塞进 session？更进一步，Akashic 是怎么既保留这些事实、又避免污染长期 history 的？

本课目标

  • 区分 runtime 内部消息、session 持久化消息、未来 turn 的 model-facing history 三层边界
  • 读懂 Akashic 如何把 tool 执行事实压缩到 tool_chain，再在 get_history() 时按需要重建
  • 对照当前 Amadeus：已经收了什么，缺了什么

先抓一句话：“不把 tool 中间消息当普通 session 消息直接存” 不等于 “这些信息以后不要了”。真正关键的是它们以什么形态被保留，以及未来喂回模型时怎么重建。

先把三层边界分开

1. Runtime 内部消息

这类消息服务于当前这一轮 loop。例如 assistant 的 tool_calls 和 tool result，它们会进入 loop_messages 让 LLM 继续思考。

2. Session 持久化消息

这类消息要长期留在会话存储里，供未来检索、记忆整合、对话恢复使用。它不一定和 runtime 内部消息一一相同。

3. Future turn 的 model-facing history

这类消息是下一轮再调 LLM 时真正送进去的上下文。它可能由 session 里的长期数据重建出来，而不是把原始运行时中间消息原样复用。

Akashic 的真实做法

先看三个关键锚点，而且必须按顺序看，不然很容易只记概念、不懂实现：

  • agent/lifecycle/phases/after_reasoning.py:147-172：assistant 持久化时把 tool_chain 挂到 assistant message 上，同时更新 session runtime metadata
  • session/store.py:572-641：数据库层把 tool_chain 单独写进 messages.tool_chain 列，而不是混在普通 content 里
  • session/manager.py:246-287：Session.get_history() 再把 tool_chain 展开回 assistant/tool 消息序列
当前 turn 内：
messages
-> assistant(tool_calls)
-> tool(result)
-> final assistant reply

持久化时：
assistant reply + tool_chain

未来取 history 时：
tool_chain
-> rebuild assistant(tool_calls)
-> rebuild tool(result)
-> append final assistant reply

也就是说，Akashic 的设计不是“tool 中间消息彻底不进历史”，而是：

  1. 不把它们当作原始普通消息直接长期散落存储
  2. 把“执行后的事实”压缩成 tool_chain
  3. 等未来真的需要给模型恢复上下文时，再从 tool_chain 重建成模型认识的 assistant/tool 协议消息

Akashic 代码精读：第 1 段，assistant 是怎么被持久化的

先看 agent/lifecycle/phases/after_reasoning.py:147-154。这里不是在保存 raw tool 消息，而是在保存 最终 assistant 回复 + 结构化的 tool_chain： 

assistant_kwargs = {
    "tools_used": list(ctx.tools_used) if ctx.tools_used else None,
    "tool_chain": list(ctx.tool_chain) if ctx.tool_chain else None,
}
if ctx.thinking is not None:
    assistant_kwargs["reasoning_content"] = ctx.thinking
session.add_message("assistant", ctx.reply, **assistant_kwargs)

这里最关键的判断是：Akashic 没有把 loop 里的每条 assistant/tool 中间消息逐条再 append 进 session。 它只保存最终 assistant message，但这个 assistant message 上多挂了几个运行时字段：

  • tools_used：这轮调用过哪些工具
  • tool_chain：这轮工具执行事实的结构化记录
  • reasoning_content：如果 provider 给了 thinking，也一起保存

也就是说，Akashic 的 assistant 持久化不是“纯文本 assistant 回复”，而是“用户可见回复 + 运行时结构化附加事实”。

Akashic 代码精读：第 2 段，tool_chain 是怎么落库的

再看 session/store.py:572-641。这里最值得学的点是：Akashic 没把 tool_chain 塞进 content 字符串，也没只塞进松散的 extra JSON，它给了它一个正式列： 

INSERT INTO messages (
    id, session_key, seq, role, content, tool_chain, extra, ts
) VALUES (?, ?, ?, ?, ?, ?, ?, ?)

写入时会先单独序列化：

tool_chain_payload = (
    json.dumps(tool_chain, ensure_ascii=False)
    if tool_chain is not None
    else None
)

这说明在 Akashic 里，tool_chain 不是一个可有可无的小附属字段，而是被当成正式持久化数据对待。 这也解释了为什么后面它能在 get_history() 里被稳定重建。

Akashic 代码精读：第 3 段，future history 是怎么重建出来的

真正的关键在 session/manager.py:246-287。这段代码说明 Akashic 的思路不是“历史里没有 raw tool 消息，所以模型以后看不到”，而是“未来需要时，我从 tool_chain 重建给模型看”。

逻辑顺序是这样的：

  1. 先拿到某条 assistant message 上的 tool_chain
  2. 遍历每个 group，每个 group 对应一轮工具调用
  3. 先重建一个 assistant message，里面带 tool_calls
  4. 再为每个 call 重建一个 role=tool 的结果消息
  5. 最后，如果这条 assistant 自己还有最终回复文本，再把最终 assistant reply 追加进去
tool_chain = m.get("tool_chain") or []
for group in tool_chain:
    calls = group.get("calls") or []
    assistant_msg = {
        "role": "assistant",
        "content": group.get("text"),
        "tool_calls": [...]
    }
    out.append(assistant_msg)
    for c in calls:
        out.append({
            "role": "tool",
            "tool_call_id": c["call_id"],
            "content": _truncate_tool_result(c.get("result", "")),
        })

if content:
    assistant_msg = {"role": "assistant", "content": content}
    out.append(assistant_msg)

这里有个非常重要的细节：Akashic 不是只重建工具结果，它连当时那轮 assistant 发起 tool_calls 的消息也一起重建。 这是为了把完整因果链恢复给模型看。

Akashic 还多做了一层：session metadata 摘要

after_reasoning.py:158-172 还会调用 update_session_runtime_metadata()，把这轮工具调用的一些摘要写进 session metadata。 对应 agent/core/passive_support.py:185-200： 

call_count = sum(
    len(group.get("calls") or [])
    for group in tool_chain
)
md["last_turn_tool_calls_count"] = call_count
md["last_turn_ts"] = datetime.now().astimezone().isoformat()

这一层不是给 LLM 直接看的主 history，而是给 runtime / telemetry / 其他策略层用的摘要信息。 所以你要区分：

  • tool_chain：保留完整执行事实，未来可重建模型历史
  • session.metadata：保留摘要信息，服务运行时策略和观测

为什么不能把原始 tool 中间消息直接当普通历史保存

  • 它们属于 runtime 协议细节，直接长期铺在 session 里，会让长期历史噪音很大。
  • tool result 往往很长，原样长期累计会挤爆上下文窗口。
  • 很多中间消息只对“当前调用链因果关系”重要，不一定适合长期以原始形态保存。
  • 真正需要留住的是“发生了哪些工具调用、关键参数是什么、结果摘要是什么”，这正是 tool_chain 这种结构化记录的价值。

当前 Amadeus 在哪一步

机制 当前状态
当前 turn 内 tool loop 已具备。runtime.py 里会把 assistant tool call 和 tool result 追加进 loop_messages。
assistant 持久化带 tool_chain 已具备。当前 assistant extra 已会保存 tool_chain。
session 中是否直接存 raw tool 消息 没有。当前 session 只持久化 user / assistant。
未来 get_history() 是否会从 tool_chain 重建 assistant/tool 协议消息 还没有。 当前只是把 tool role 过滤掉，并没有像 Akashic 那样重建模型可读 history。

对应证据： amadeus/session.py:39-50、 amadeus/runtime.py:101-107、 tests/test_runtime.py:368-456。

这正是当前的关键 Gap

当前 Amadeus 已经做对了一半：

  • 没有把 tool 中间消息直接混进普通 session 历史
  • 已经把执行事实保存成了 tool_chain

但还没做完另一半：

  • 未来 turn 再取 history 时，当前并不会从 tool_chain 重建 assistant/tool 消息序列
  • 这意味着过去的工具执行链虽然被记录了，但还没有正式回到 model-facing history 里

所以 Lesson 11 的核心不是“要不要把 tool 中间消息存起来”，而是：要以什么形态存，未来再以什么形态喂回模型。

最容易犯的 3 个错

  1. 以为 tool 中间消息既然参与过 loop，就应该原样永久写进 session history。
  2. 以为不把 raw tool 消息直接存进 session，就等于这些信息以后彻底没用了。
  3. 以为当前 Amadeus 已经和 Akashic 一样处理了历史重建。其实现在只做到了“记录了 tool_chain”，还没做到“从 tool_chain 重建 history”。

你现在必须能复述的 4 个问题

  1. 为什么 tool 中间消息要参与当前 loop？
  2. 为什么又不应该默认把它们当普通聊天历史原样长期保存？
  3. Akashic 是怎么把这些执行事实保留下来的？
  4. 当前 Amadeus 已经做到哪一半，还差哪一半？
