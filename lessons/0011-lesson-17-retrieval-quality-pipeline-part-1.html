前情回顾：Amadeus 当前检索有多"简化"

先看你已经在 Amadeus 里实现过的检索路径（amadeus/vector_memory.py）：

async def query(self, query: MemoryQuery) -> MemoryQueryResult:
    query_vector = await self.embedding_provider.embed(text)
    rows = self.store.list_active(kinds=query.kinds)
    records = _rank_rows(rows, query_vector, text, limit=limit, threshold=self.score_threshold)
    return MemoryQueryResult(records=records, trace=trace)

这个流程是：

embed → list_active → rank（max score of vector or keyword）
一次 embedding，一次全表扫描，对每条结果取 max(cosine, keyword_score)，不区分 lane，不做多查询改写，不做融合，不做 sufficiency 判断。

这不是"勉强能用"的问题——它缺少 agent 级检索必须的四个能力：

  • 查询改写：用户说"之前那个仁王的事情"需要改写为"用户与仁王游戏的讨论记录"才能命中记忆。
  • 双路召回：纯向量可能漏掉精确关键词匹配，纯关键词可能漏掉语义相似但用词不同的条目。
  • RRF 融合：两路结果各自排序后需要统一排序，不能简单拼接。
  • Sufficiency 判断：检索到的内容是否足够回答用户问题？不够的话需要改写查询重新检索。

Lesson 17 就是为补这四个能力开始的。下面进入 Akashic 源码课。

下面逐个组件讲。

组件 1：Query Rewriter（memory2/query_rewriter.py）

这是检索管线的"第一道门"。用户的自然语言消息很少是好的检索查询。"我之前聊过什么关于仁王的内容"需要改写为"用户与仁王游戏相关的讨论历史"才能在向量空间命中。

双路改写

Akashic 的 QueryRewriter 同时做两个独立的 LLM 调用：

class QueryRewriter:
    async def decide(self, user_msg: str, recent_history: str) -> GateDecision:
        # 并行两路：history query rewrite + procedure query rewrite
        main_task = asyncio.create_task(
            self._call_llm(self._build_prompt(user_msg=user_msg, recent_history=recent_history))
        )
        procedure_task = asyncio.create_task(self._rewrite_procedure_query(user_msg))
        done, pending = await asyncio.wait(
            {main_task, procedure_task}, timeout=self._timeout_s,
        )
        # ... 解析 decision 和 procedure_query
  • History 路：判断是否要检索历史事件，输出 decision（RETRIEVE/NO_RETRIEVE）和 history_query（改写后的查询）。
  • Procedure 路：独立把用户消息改写为 procedure/preference 库可命中的 summary 风格查询（如"用户要求 agent 下载外部资源"）。
  • 隔离设计：一路失败不影响另一路。history 路超时则 fallback 原始消息，procedure 路超时则返回空字符串。

为什么需要两路隔离？

用户的同一句话可能同时触发"查历史"和"写规则"两个意图。例如用户说"以后讲复杂问题先给例子"——这不需要查历史（NO_RETRIEVE），但需要写入 preference。两路隔离让 procedure 的改写不被 history 的 decision 阻塞。

对比 agent/policies/history_route.py 的 HistoryRoutePolicy，它是被动 loop 级别的路由决策器，更轻量——只输出 needs_history/rewritten_query，不做 procedure 改写。它的职责是"往 context 里是否注入 retrieval block"，而 QueryRewriter 的职责是"检索前优化查询"。

组件 2：HyDE Enhancer（memory2/hyde_enhancer.py）

HyDE（Hypothetical Document Embeddings）是检索增强的核心技巧。它不是在查完之后才优化，而是在查之前先生成一条"假想的理想记忆条目"，用这条假想条目再做一次检索。

工作原理

async def augment(self, *, raw_query, context, retrieve_fn, top_k) -> HyDEAugmentResult:
    # 并行：raw 检索 + LLM 生成假想条目
    raw_task = asyncio.create_task(retrieve_fn(raw_query, top_k=top_k))
    hyp_task = asyncio.create_task(self.generate_hypothesis(raw_query, context))
    raw_hits, hypothesis = await asyncio.gather(raw_task, hyp_task)

    if not hypothesis:
        return HyDEAugmentResult(items=raw_hits, used_hyde=False)

    # hypothesis 就绪后串行发起第二次检索
    hyde_hits = await retrieve_fn(hypothesis, top_k=top_k)
    merged = _union_dedup(raw_hits, hyde_hits)
    return HyDEAugmentResult(items=merged, used_hyde=len(merged) > len(raw_hits))
  1. 并行：原始 query 检索 + LLM 生成假想记忆条目，互不等待。
  2. 假想条目例如：用户问"我之前和你聊过什么有关仁王的内容吗" → LLM 生成"用户讨论了仁王的游戏机制和战斗系统难度"。
  3. 串行第二次检索：用假想条目做 query 再做一次向量检索。
  4. Union dedup：保留 raw 全部结果（含原始分数），只追加 hyde 中 raw 没有的条目。不修改任何条目的 score，避免影响下游注入筛选的 type_best 计算。
  5. Timeout/fail-open：hypothesis 生成超时或失败 → 降级返回 raw 结果，used_hyde=False。不阻塞主路径。

关键设计参数

属性值动机
prompt 约束肯定式、第三人称、"用户..."、简洁事实陈述生成的假想条目的 embedding 与真实记忆的 embedding 在同一个语义空间内
max_tokens80假想条目只需要一句话，不需要大段生成
timeout2.0s快速失败，不拖慢主回复
light_provider独立的轻量 LLM不用主模型，省成本、低延迟
union_dedup保留 raw 分数避免 hyde 的高分污染 raw 的排序

HyDE 在 _query_answer() 中的位置比较特殊：它直接在 engine 层内嵌了两个 hypothesis 生成，而不是通过 HyDEEnhancer 类。这被叫做"显式 HyDE"（_gen_hypothesis）。Amadeus 复现时应当从显式 HyDE 开始。

组件 3：双路召回与 RRF 融合（memory2/retriever.py）

这是检索管线的核心——实际从数据库里找东西的地方。Akashic 的 Retriever 同时维护两条召回路径：

retrieve(query, aux_queries, ...)
↓ 分岔
向量 lane（dense）
embed → vector_search_batch
主 query + aux_queries
逐路 max-pool → seen dict
关键词 lane（sparse）
term extract → keyword_search
bigram/ASCII token → BM25 风格
↓ 汇合
RRF merge(vector_items, keyword_items, top_n=actual_top_k)

向量 lane（dense retrieval）

async def _retrieve_vector_lanes(self, query_texts, ...):
    # 多路 query 并行 embedding
    vectors = await self._embed_lanes(query_texts)
    # vector_search_batch 批量查询
    hit_groups = self._store.vector_search_batch(vectors, ...)
    # max-pool：同 id 保留最高分
    seen = {}
    for hits in hit_groups:
        for hit in hits:
            _remember_vector_hit(seen, hit)
    return list(seen.values())
  • 多路 embedding：原始 query + aux_queries（HyDE hypothesis）一起并发 embedding，不串行。
  • vector_search_batch：在 SQLite 中用 sqlite-vec 做批量余弦相似度搜索。
  • hotness 加权：在排序时同时考虑 semantic score（向量相似度）和 hotness score（reinforcement × 时间衰减）。final = (1-α) × semantic + α × hotness。
  • 向后兼容：α=0 时纯 cosine，hotness 不影响排序。

关键词 lane（sparse retrieval）

def _retrieve_keyword_lane(self, query, ...):
    terms = _extract_terms(query)  # bigram + ASCII token
    if not terms:
        return []
    return self._store.keyword_search_summary(terms, limit=max(30, top_k*2))
  • Term 提取：英文按 token 切分，中文按 bigram（双字）切分，过滤 CJK 停用词。
  • SQL 搜索：summary LIKE '%term%' 模式，命中词数计分。
  • 高于 top_k 的 limit：关键词路用更宽的候选池（max(30, top_k×2)），为 RRF 提供更多候选。

RRF 融合（Reciprocal Rank Fusion）

def _rrf_merge(vector_items, keyword_items, *, top_n, k=60):
    for item_id in set(vec_rank) | set(keyword_rank):
        rrf_score = 0.0
        if item_id in vec_rank:
            rrf_score += 1.0 / (k + vec_rank[item_id])
        if item_id in keyword_rank:
            rrf_score += _KEYWORD_RRF_WEIGHT / (k + keyword_rank[item_id])
        scored.append((item_id, rrf_score, ...))
    return sorted(scored, key=lambda x: x[1], reverse=True)[:top_n]
  • RRF 不是简单拼接：它在两路的 rank 位置之间做加权调和。一条结果如果在两路都出现在中排，它的 RRF 分数可能高于在一路排第一但在另一路完全没出现的结果。
  • 关键词权重 0.5：关键词路的 RRF 贡献减半，因为关键词的召回精度通常低于向量路。
  • k=60：Akashic 使用较大的 RRF 常数（标准 RRF 通常用 k=60），避免低排名结果贡献过高。
当前 Amadeus 差距：_rank_rows 用 max(vector_score, keyword_score)，不是 RRF。这意味着一条结果如果在向量路得了 0.7 分、在关键词路得了 0.7 分，它和只在向量路得了 0.8 分的结果相比，前者可能更相关（双路证实），但 max 策略会选后者。

组件 4：Sufficiency Checker（memory2/sufficiency_checker.py）

检索完成之后，Akashic 不会直接认为"结果够了"。Sufficiency Checker 检查检索到的内容是否足以回答用户的问题。

触发条件

def should_check_sufficiency(items: list[dict]) -> bool:
    if not items: return True       # 无结果 → 必须查
    if _has_forced_procedure(items): return False  # 有强制 tool 约束 → 不查
    return False                    # 有正常结果 → 不查

关键设计：sufficiency check 只在"完全无结果"时触发，而不是对每次检索都做。原因是 Akashic 的注入阶段已经在 type_best 筛选和 score_threshold 过滤中完成了质量判断。

LLM 判断逻辑

async def check(self, query, items, context="") -> SufficiencyResult:
    prompt = self._build_prompt(query=query, items=items, context=context)
    response = await asyncio.wait_for(
        self._llm_client.chat(messages=[{"role": "user", "content": prompt}], ...),
        timeout=self._timeout_s,
    )
    parsed = self._parse_output(response)
    # yes → sufficient; partial → sufficient; no → insufficient + refined_query
    return SufficiencyResult(is_sufficient=..., refined_query=..., ...)
  • 三元输出：yes|no|partial——sufficient、明确不足、部分相关。
  • Refined query：当判断为 "no" 时，LLM 同时输出改写后的查询，用于重新检索。
  • Fail-open：LLM 输出乱码或异常时视为 sufficient，不阻断主路径。
  • timeout 600ms：超时极短——它只是一个轻量 "能不能用" 质检，不是完整推理。

组件 5：Injection Planner（memory2/injection_planner.py）

这是检索管线的调度层，协调 scope 路由、HyDE、multi-query retrieval。

Scope 路由

调用 retrieve_history_items 时，有三种可能的 scope_mode：

scope_mode含义触发条件
scoped只查当前 channel/chat 内的记忆有 scope 且优先 scope 时命中
global-fallbackscope 无结果，回退全局检索prefer_scoped 但 scoped 为空，allow_global=True
global+hyde全局 + HyDE 增强hyde_enhancer 存在且实际追加了新条目

Procedure Multi-Query

async def retrieve_procedure_items(memory, query="", queries=None, *, top_k):
    tasks = [memory.retrieve_related(q, memory_types=["procedure", "preference"], top_k=top_k) for q in active_queries]
    raw_results = await asyncio.gather(*tasks)
    return sorted(pooled, key=lambda item: item.score, reverse=True)[:top_k]

procedure 检索支持一次传入多个 query。多个 query 的结果通过 max-pool 合并——同一个条目被不同 query 命中时保留最高分。

组件 6：Structured Injection Block（memory2/retriever.py 的 build_injection_block）

检索到的条目最终要注入到 LLM 的 context 里。Akashic 不是把所有结果简单拼成列表，而是做了结构化格式化：

def build_injection_block(self, items) -> tuple[str, list[str]]:
    selected, forced, norms, events = self._select_injection_sections(items)
    parts = self._build_section_parts(forced, norms, events)
    return self._apply_char_budget(parts, has_forced=bool(forced))

三段式注入

区块标题内容特征
【强制约束】有 tool_requirement 的 procedure必须执行，不超预算截断
【流程规范】preference、procedure（无 tool_requirement）按 score 降序，最多 4 条
【相关历史】event、profile最多 2 条，附加时间戳
  • 字符预算：默认 1200 字符上限，超过时从低优先级区块开始截断。强制约束区块永不截断。
  • 置信度标记：如果 score 处于阈值附近（score < threshold + delta），LLM 会看到"有印象，不确定"标记，避免盲目信任边缘结果。
  • 证据标记：每条结果附带 source_ref 和"可回源原文"标记，LLM 可以用 fetch_messages 验证。

完整调用链：_query_context 和 _query_answer

现在看 engine 层怎么把以上组件串起来。

_query_context（被动预检索路径）

async def _query_context(self, request: MemoryQuery) -> MemoryQueryResult:
    queries = self._resolve_queries(request)
    items = await self._retrieve_related(request.text, ..., aux_queries=queries[1:])
    text_block, injected_ids = retriever.build_injection_block(items)
    return MemoryQueryResult(text_block=text_block, records=records, trace=...)

被动路径：在主循环的 context 构建阶段调用，不需要 LLM 主动触发。结果作为 prompt block 注入。

_query_answer（recall_memory tool 路径）

async def _query_answer(self, request: MemoryQuery) -> MemoryQueryResult:
    hyp1 = asyncio.create_task(self._gen_hypothesis(request.text, style="event"))
    hyp2 = asyncio.create_task(self._gen_hypothesis(request.text, style="general"))
    aux_queries = [text for text in (await asyncio.gather(hyp1, hyp2)) if text]
    hits = await self._retrieve_related(request.text, aux_queries=aux_queries, keyword_enabled=True)
    sliced = list(hits)[: request.limit]
    return MemoryQueryResult(records=[self._build_record(item) for item in sliced], ...)

工具路径：由 LLM 主动调用 recall_memory 触发。生成两条 hypothesis（event 风格 + general 风格），然后走同一条 Retriever.retrieve() 路径。

两路最终都调用同一个 _retrieve_related → retriever.retrieve()（向量 + 关键词 + RRF）。复用是核心设计：不因为入口不同就维护两套检索逻辑。

Retrieval Trace 与可观测性

Akashic 在每个检索步骤中都会记录 trace，最终汇总为 RetrievalTrace：

class RetrievalTrace:
    gate_type: str | None          # "auto" | "tool"
    route_decision: str | None     # "scoped" | "global" | "global+hyde"
    rewritten_query: str | None    # QueryRewriter 改写后的 query
    injected_count: int            # 实际注入 context 的条目数
    raw: dict | None               # 原始检索事件（含 candidate_count 等）

这使开发者能追溯每次 turn 的检索行为：

  • QueryRewriter 是否触发了？改写成了什么？
  • HyDE 是否参与？hypothesis 是什么？
  • 双路召回了多少候选？RRF 融合后最终注入了几条？
  • Sufficiency check 是否通过？

Part 2 复现建议

一次复现完整管线是不现实的。建议按以下顺序分步推进，每步都做 focused test 验证：

  1. 升级 Retriever：把 VectorMemoryEngine.query() 中的 max(vector, keyword) 替换为真正的 RRF 融合。补充术语提取（bigram + 停用词）和 keyword_search 的 SQL 查询。
  2. 添加结构化注入：把 render_context_block() 从简单列表改为三段式格式化（强制约束 / 流程规范 / 相关历史），加上字符预算。
  3. 添加 Query Rewriter：用轻量 LLM 做查询改写（是否需要检索 + 改写查询）。先用一个简单的 prompt 实现历史查询改写，再补 procedure 改写。
  4. 添加 HyDE：在 recall_memory 工具路径中先生成一条假想条目再检索，union_dedup 合并。
  5. 添加 Sufficiency Check：零结果时调 LLM 判断是否需要重查。

不阻塞的前提：以上每一步都要保证"改了之后原有测试仍然通过"。不能因为加了 RRF 就丢失基本的关键词召回能力。

常见误区

  • 误区：query rewrite、HyDE、sufficiency 是一件事。纠正：rewrite 改查询文本，HyDE 生成假想 memory，sufficiency 判断结果够不够。
  • 误区：有 vector 就不需要 keyword。纠正：ID、文件名、工具名、source_ref 通常更依赖 lexical lane。
  • 误区：RRF 是算一个更准的相似度。纠正：RRF 融合的是排名，不是替代 vector score。
  • 误区：路线图写 BM25 就说明 Akashic 已经用 BM25。纠正：当前源码是 OR-LIKE keyword_score；BM25 是后续可升级方向。
  • 误区：HyDE 失败就应该报错。纠正：Akashic 这里必须 fail-open，否则检索增强会反过来破坏基础 retrieval。
