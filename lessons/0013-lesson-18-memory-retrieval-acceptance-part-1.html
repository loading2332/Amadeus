  • 理解摘要、搜索预览、定位合同和原始消息的证据等级。

真实主动链路

用户询问具体历史事实
  → recall_memory(query)
  → 候选 MemoryRecord + memory ID + evidence/source_ref
  → fetch_messages(evidence 或 source_ref)
  → 原始 session messages + 上下文
  → 基于原文回答

recall 不足
  → search_messages(query)
  → 候选预览 + source_ref
  → fetch_messages(source_ref)
  → 基于原文回答

Akashic 把工具描述当作 schema 的语义部分：字段类型只说明“能传什么”，description 还必须说明“什么时候允许把结果当证据”。

候选与证据等级

产物作用能否直接作为最终证据
被动 memory block给模型预先背景，帮助决定关注方向否；它是整理后的记忆
recall summary语义检索候选，带 memory ID否；可能压缩、过时或互相冲突
search preview关键词定位候选消息否；预览可能截断且缺少上下文
evidence/source_ref把候选连接到原始消息否；它是定位合同，不是正文
fetch original messages返回持久化原文及邻近上下文是；这是本链路的最终证据

资深工程师会先检查“证据能否回源”，而不是先看召回分数。分数只表示候选相关性，不证明候选内容真实、完整或仍然有效。

Memory ID 与 Message ID

Memory ID
标识整理后的记忆条目。它由 recall_memory 返回，也是 forget_memory 的删除目标。
Message ID
标识原始会话消息。它由 source_ref/evidence 解析并交给 fetch_messages，用于读取原文。
memory ID  → forget_memory → supersede 记忆条目
message ID → fetch_messages → 读取原始消息

禁止：forget_memory(message ID)

纠错不是删除历史。正确流程是定位旧记忆、回看来源、确认错误，再失效派生出来的 memory record；原始 session message 仍然保留，作为审计依据。

工具 schema 能强制字段形状，却不能单独强制跨多次 tool call 的时序。当前 Amadeus 用 prompt 明确顺序，用验收测试锁定描述合同；如果后续需要强一致性，应迁移 Akashic citation/runtime policy 的对应扩展点，而不是继续堆提示词。

Amadeus 验收与最小修复

先写六个联合验收场景。首次运行时，三个数据路径测试通过，三个语义合同测试失败：

场景首次结果结论
recall evidence → fetch 原文通过resolver 数据链已接通
search source_ref → fetch 原文通过lookup 工具合同可消费
纠错后仅失效 memory ID通过原始 session 与 message ID 保留
工具描述区分候选与证据失败模型看不到明确 evidence boundary
behavior prompt 固化调用顺序失败跨工具时序没有显式协议
recall 输出完整引用 metadata失败Amadeus 输出合同弱于 Akashic

最小修复范围

  • amadeus/tools/recall_memory.py：声明 summary 是候选；evidence 补齐 source_ref 与 metadata；返回 citation metadata。
  • amadeus/tools/defaults.py：明确 search preview 不能直接作证，fetch 才返回最终原文。
  • amadeus/prompts/__init__.py：新增 History Retrieval Protocol，固化 recall/search/fetch/forget 顺序。
  • tests/test_memory_retrieval_acceptance.py：用生产工具和真实 SQLite store 验收跨工具合同；没有用 fake 替代生产机制。

取舍：本次选择局部合同修复，不重写 memory architecture。优点是失败与修复一一对应；代价是调用时序仍部分依赖模型遵守 prompt，citation runtime enforcement 留作明确 gap。

验证步骤与当前证据

  1. 运行验收：uv run --extra dev pytest tests/test_memory_retrieval_acceptance.py -q。预期 6 passed。
  2. 运行 memory/retrieval focused suite。当前证据：38 passed。
  3. 运行全量：uv run --extra dev pytest -q。当前证据：125 passed。
  4. 运行规范检查：uv run --extra dev ruff check .。当前证据：All checks passed。
  5. 运行类型检查：uv run --extra dev mypy。当前证据：59 source files，无错误。

手工观察时不要只看“测试通过”：检查 recall JSON 是否同时有 memory ID、evidence.source_ref 和 citation metadata；检查 fetch 输出是否出现完整 content；检查 forget 后原始 session message 是否仍可读取。

常见误区与排错顺序

  • 召回分高就是真相：分数只排序候选，矛盾或关键事实必须回源。
  • source_ref 就是原文：它只是定位器；必须交给 fetch 解析。
  • search preview 足够回答：预览可能被截断，也没有相邻上下文。
  • 纠错就删除消息：消息是历史证据；应失效由它派生的 memory record。
  • schema 能保证工具顺序：schema 只能约束单次参数，跨调用顺序需要 prompt 或 runtime policy。

自己排错的前三步：先看 tool 输出的 ID 属于哪一层；再检查 source_ref/evidence 能否被 fetch 消费；最后检查 prompt 或 runtime 是否要求模型按正确顺序调用。

简历可讲述版本

参考 Akashic 的 evidence-first memory retrieval 设计，在 Amadeus 中建立 recall/search 候选到原始 session message 的可追溯链路；通过联合验收锁定 source_ref、memory ID 与 message ID 的边界，并补齐候选/证据描述和引用 metadata。全量 125 个测试、静态检查与类型检查通过，同时明确保留 citation runtime enforcement 和数据库级检索性能 gap。
