对应总计划 Lesson 12 Part 1

Akashic Context Trim 与 Context-Length Retry 源码课

这节课先不写新功能，先把 Akashic 在被动对话里如何处理“上下文超长”讲透。重点不是“裁剪一点历史”这么简单，而是完整理解 provider 识别错误 -> reasoner 持有 retry 主控权 -> trim plan 逐级降载 -> 成功后把收口结果写回 session/runtime metadata。

当前阶段地图

  • 已经实现：多步 tool loop、tool_chain 持久化、从 tool_chain 重建未来 turn 的 model-facing history。
  • 当前主链：amadeus/runtime.py 已经能跑 LLM -> tool -> LLM，但还缺少“超长上下文时自动降载并重试”的外层控制。
  • 半成品能力：Amadeus 已经有 ContextLengthError 识别、已有 trim plan 生成函数、已有 disabled_sections / history_window 渲染能力，但这些拼图还没接进被动 loop 主链。
  • 下一个 Akashic 对齐切片：把 context-length failure 从“直接炸掉的一次错误”变成“reasoner 可控的阶段性重试流程”。

为什么先做这个：因为 Lesson 10 和 Lesson 11 已经把 loop 与持久化边界铺好，下一步最真实的工程压力点就是“prompt 变长后系统怎么退化而不直接死掉”。

与 Mission 的关系

你的目标不是做一个“能跑一下”的 demo，而是亲手复现 Akashic 的复杂架构，最后能把 Amadeus 当成自己讲得清的简历项目。 context trim 恰好是这类 agent 系统里的真实复杂度来源之一：它逼你同时处理 provider 边界、prompt 结构、history 策略、失败恢复和可观测性。

provider.chat(...)

第一层：provider 只负责识别，不负责重试决策

Akashic 在 agent/provider.py:38-54 定义了 _CONTEXT_LENGTH_KEYWORDS 和 ContextLengthError。 真正的意思很朴素：

provider 的职责

把不同厂商报出来的“超长上下文”错误统一翻译成一个稳定异常类型，给上层流程判断。

provider 不该做的事

它不应该自己决定删哪段 history、关哪块 prompt section，也不应该暗自重试，因为这些都属于 agent 编排层。

人话版：provider 只说“炸的是上下文长度”，但“怎么降载、先砍谁、失败后怎么记账”必须交给 reasoner。

第二层：trim plan 不是临时补丁，而是预先定义的降载顺序

Akashic 在 agent/prompting/budget.py:12-27 明确写了 DEFAULT_CONTEXT_TRIM_PLANS： full -> trim_skills_catalog -> trim_memes -> trim_long_term_memory -> trim_retrieved_memory。

设计点 Akashic 的意思
先删动态大块 先砍 skills_catalog、memes、记忆块，而不是一上来先动核心人格/规则。
核心区不乱动 系统最核心的 identity / rules 要尽量保住，否则虽然短了，但 agent 也变味了。
顺序是产品决策 不是谁大就先删谁，而是谁“对当前轮价值更低、对 agent 身份伤害更小”就先删谁。

第三层：真正的主控权在 DefaultReasoner.run_turn()

Akashic 的关键代码在 agent/core/passive_turn.py:750-913。这段逻辑的本质是：

  1. 先拿到 source_history，并初始化 retry_trace。
  2. 调用 _build_attempt_plans(total_history) 生成一串 attempt。
  3. 每个 attempt 都会带着新的 history_window 和 disabled_sections 再次调用 prompt render。
  4. 如果 run() 成功，记录 selected_plan、trimmed_sections、llm_user_content、llm_context_frame、react_stats。
  5. 如果是后续 attempt 才成功，还会把 session 历史收口到成功窗口，再保存 session。
attempts = self._build_attempt_plans(total_history)
for plan in attempts:
    history_for_attempt = self._slice_history(source_history, plan["history_window"])
    prompt_render = render(..., history=history_for_attempt, disabled_sections=plan["disabled_sections"])
    try:
        result = run(prompt_render.messages)
        if attempt > 0:
            trim session.messages to successful window
        return TurnRunResult(..., context_retry=retry_trace)
    except ContextLengthError:
        continue with next plan

重点不是“捕获异常后再来一次”，而是“每次重试前都重新构造 prompt，而不是粗暴改现成 message 列表”。

第四层：为什么要先 trim section，再 trim history

Akashic 在 agent/core/passive_turn.py:1709-1738 里构造 attempt plan 时，顺序非常明确：

  • 前几轮先保持完整 history window，只逐步关闭低优先级 section。
  • 只有删到最后一层了，才开始按比例缩 history window。
  • 比例来自 _SAFETY_RETRY_RATIOS，本质是在“尽量保因果链”与“必须缩短输入”之间做折中。

这说明 Akashic 默认认为：最近对话因果链通常比某些辅助 prompt 块更值钱。所以先删外设，再动历史。

第五层：重试成功以后，为什么还要修 session

这是最容易被忽略的一点。在 agent/core/passive_turn.py:837-849，如果不是第一次 attempt 才成功，Akashic 会把 session.messages 修剪到成功的 window，并立刻保存。

不是只为了这一次成功

它是在把“这轮已经证明过太长”的事实写回 session，让下一轮从更现实的基线继续。

这也是可观测性

selected_plan、trimmed_sections、react_stats 会进入 context_retry，后续 phase 和观测层都能看到。

第六层：Akashic 不把它当硬错误，而是阶段性事实

你前面已经抓住这个点了。这里再固定成一句工程话：

context-length failure 在 Akashic 里首先是一个“需要调整输入预算的运行时事实”，不是一个立即终止整个被动 turn 的架构性失败。

所以它才会进入 context_retry，才会被后续生命周期模块继续消费，而不是简单抛栈结束。

能力 当前 Amadeus 状态

这就是 Lesson 12 的实现目标边界：不是发明新 prompt 系统，而是把现有三块拼图 provider 异常、prompt budget、context render 接入 PassiveRuntime.run_turn()。

当前阶段验证证据

  • Akashic：tests/test_safety_retry_service.py 已经验证“超长后先 trim 动态 section，再重试成功”。
  • Amadeus：tests/test_prompt_budget.py 已经验证 trim attempt 构造；tests/test_provider.py 已覆盖 provider 基础行为，但还没有 runtime 级的 context retry 集成测试。

这节课最容易误解的点

  • 误以为应该把自动重试写进 provider。错，provider 只知道错误类型，不知道 prompt 结构和 session 边界。
  • 误以为超长了就直接砍 history。错，Akashic 先删低优先级动态区块，尽量保住最近对话因果链。
  • 误以为重试只是“把 messages 列表切短一点”。错，正确做法是重新 render，让 disabled_sections、history_window、上下文块一致生效。
  • 误以为 retry 成功就结束了。还没完，成功后的 trim 结果要反映回 session 和观测数据。

你现在必须能复述的 5 个问题

  1. 为什么 ContextLengthError 的识别在 provider，而 trim / retry 的主控在 reasoner？
  2. 为什么 Akashic 先删 prompt section，再删 history window？
  3. 为什么每次 retry 前必须重新 render prompt，而不是直接就地改旧 messages？
  4. 为什么 retry 成功后还要把成功窗口写回 session，并记录 selected_plan？
  5. 当前 Amadeus 已经具备哪三块拼图，还缺哪一块主链控制？
