Hotel Azure：那张不再写序号的施工白板

1. 原本只要一张顺序表

Hotel Azure 每天都要翻新一批客房。工程经理老蔡把流程写成六行：前台领房卡、资料室调取房间记录、设计组生成施工单、各部门开协调会、秘书汇总会上追加的要求、值班经理签字交房。

这套顺序用了很多年。每支内部队伍都知道自己是第几步，所以老蔡只需在早会上说：“今天还是 1 到 6，照旧。”

直到酒店开始接入外包团队。

2. “把我排在第几位”很快失效了

第一家外包商负责智能门锁。他们说：“拿到房卡以后我们才能检测，但必须赶在设计组画施工单之前。把我们排在第 2 位吧。”

第二天，酒店又请来消防复核队。他们必须看完房间记录才能进场，却不关心门锁是否检测完。第三天，客户关系部增加了一名撤单专员：只要发现客人临时取消翻新，就要在领到房卡后立刻结束这张工单，后面的资料调取和施工设计都不应继续。

于是“第 2 位”同时属于三支队伍。老蔡把门锁改成 2.1、消防改成 2.2、撤单改成 1.5。没过几天，协调会又拆成两个环节，所有小数都要重排。更麻烦的是，数字只说明谁在前面，却没有说明为什么必须在前面。

老蔡意识到：真正稳定的不是第几位，而是每支队伍开工前究竟在等什么。

3. 每支队伍只交一张“开工卡”

他擦掉白板上的序号，要求每支队伍改交一张卡片。卡片上先写一个不能重复的队名，然后回答两个问题：

  1. 你开工前，要看到哪一道工序已经签字？工作车上还必须放着什么材料？
  2. 你完工后，会在工作车上留下什么，供后面的人使用？

门锁队写：“等前台领卡签字；车上必须有实体房卡；完成后留下门锁检测报告。”消防队写：“等资料室调档签字；车上必须有房间记录；完成后留下消防意见。”撤单专员写：“等前台领卡签字；车上必须有房卡；若命中撤单，直接留下可交付的终止单。”

每天早上，老蔡先找出所有已经满足开工条件的卡片。做完一张，就在白板上勾掉对应工序，并把它留下的材料放上工作车。接着再看哪些卡片因此可以开工。若同一时刻有多张卡片都能开工，他按一条固定规则取卡，保证同一批卡每天都会得到同一个结果。

这时，门锁队自然落在“领卡”之后、“设计”之前；消防队可以沿另一条依赖继续；撤单专员若留下终止单，资料室和设计组看到车上已经有最终单据，就不再重复准备普通施工资料。没有人再申请“第 1.5 位”。

4. 工序和材料不能混成一件事

有天，软装队在卡片上只写：“车上要有油漆色卡。”老蔡发现，仅凭这句话无法知道色卡由谁制作，也无法保证软装队会排在制作色卡的人后面。它只说明开工时应该拿到什么，却没有建立两支队伍之间的先后关系。

他让软装队补上一句：“等设计组完成配色。”从此卡片同时保留两类信息：一道已经完成的工序负责确定顺序；工作车上的材料负责检查交接是否闭合。需要某份材料的人，通常必须同时写清是谁先完成了生产它的工作。

5. 有些贡献不值得让所有人互相认识

协调会后，经常有许多外包队想追加一句提醒。若每支队伍都直接去找秘书，秘书就必须认识所有外包商。老蔡便在工作车上放了几个带统一标签的信封：“客房提醒·门锁”“客房提醒·消防”“客房提醒·清洁”。秘书只需在固定时刻收走所有以“客房提醒”开头的信封，再合并进最终施工单。

但这不是一道上锁的隔离墙。获得信任的内部团队仍然可以直接修改施工单；信封只是宿主给扩展团队约定的一条清晰通道，让新增团队不必反过来修改秘书的代码。

6. 白板开始替老蔡暴露问题

规则建立后，几类过去要到现场才暴露的问题，在排工时就能被看见：

  • 临时灯光队写着“等舞台供应商完成”，但今天根本没有舞台供应商。它是可选外包队，于是老蔡先撤下它；所有等待灯光队的外包卡也随之撤下。
  • 某队只写“车上必须有一桶蓝漆”，却没有任何已排工序承诺留下蓝漆。白板亮起提醒，但不会凭空猜出应该把谁排到前面。
  • 两支队伍用了同一个队名。老蔡拒绝排表，因为后面的人将无法指出自己等的究竟是哪一支。
  • 木工说等电工，电工又说等木工。早会上再也找不到可以先开工的卡片，整张排表被判定无解。
  • 排表成功不代表施工一定成功。任何队伍进场后真的抛出事故，流程仍会中断；最后也必须有人交出可签字的终单，不能因为所有人都“跑过一次”就宣称房间已交付。

7. 老蔡最后才翻开白板背面的标签

新来的工程师问：“这到底是一张什么表？它不像普通待办清单，也不像按数字排的优先级。”

老蔡把白板翻过来。原来每一栏背后早有一个给系统看的名字：

  • 每支队伍独一无二的工序名，写着 slot；
  • “等哪道工序、车上要有什么”，写着 requires；
  • “完工后留下什么”，写着 produces；
  • 那辆伴随整次施工、不断装入中间材料的工作车，写着 frame.slots；
  • 每天从可开工卡片中取一张、完成后再释放下一批卡片的排法，写着 topo_sort_modules()；
  • 从接单到交出终单的整段施工，写着 Phase.run()。

读到这里你才会发现：老蔡没有发明一种更复杂的 priority。他把“我要排第几”改写成了“我依赖谁、我需要什么、我会留下什么”，再让依赖关系自己长出执行顺序。

故事之后：刚才真正讲的是 Phase Slot Engine

故事里的东西Akashic 概念真正解决的问题
不能重复的队名Module slot给可执行节点稳定身份，让其他 module 可以引用它
等某道工序签字requires 中的 module slot建立拓扑边，真正决定执行先后
车上必须已有某份材料requires 中的 data slot检查数据合同是否闭合，但不自动产生排序边
完工后留下材料produces声明后续 module 可以消费的数据
统一标签的提醒信封Export prefix + collector让多个插件按约定贡献数据，而非让宿主逐个认识插件
撤掉缺失供应商及其下游外包卡递归禁用缺失 module 依赖的 plugin modules可选扩展缺失时保住内置主链
重名、互相等待、现场事故、无人交终单重复 slot、循环依赖、module 异常、无 output分别在组装期或执行期明确失败，不静默产出错误结果
现在用一句人话收口
Phase Slot Engine 是一个“声明关系，再计算顺序”的小型执行引擎：module 用 slot 标识自己，用 requires 声明前置工序和所需数据，用 produces 声明产出；宿主把内置与插件 module 合并后做拓扑排序，再共享同一个 frame 顺序执行。

PhaseFrame / PhaseModule / Phase 三个职责

@dataclass
class PhaseFrame(Generic[I, O]):
    input: I
    slots: dict[str, Any] = field(default_factory=dict)
    output: O | None = None

class PhaseModule(Protocol[F]):
    async def run(self, frame: F) -> F: ...

class Phase(Generic[I, O, F]):
    async def run(self, input: I) -> O:
        frame = self._frame_factory(input)
        for module in self._modules:
            frame = await module.run(frame)
        if frame.output is None:
            raise RuntimeError("Phase 模块链未产生 output")
        return frame.output
  • Frame：一次 phase 调用的共享运行帧；不是全局容器。
  • Module：读取 frame、完成一个窄职责、返回 frame。
  • Phase：验证并按既定顺序执行；异常默认向上传播。

class ConsumerModule:

    requires = ("before_turn.acquire_session", "session:session")
常见错误直觉
只写 requires = ("session:session",) 不会让 consumer 自动排到 producer 后面。_module_requires() 只把当前 slot_map 中存在的 module 名加入图；data slot 只会由 Phase._validate() 检查此前是否已被声明为 produced。

零入度时到底谁先？

queue.sort(key=lambda item: (_is_builtin_slot(item), slot_order[item]))

Python 中 False < True。Plugin slot 的 _is_builtin_slot() 为 False，因此同为零入度时，当前实现会先取 plugin，再取 built-in；同一类别按原始注册顺序。这个细节让依赖 acquire_session 的命令插件有机会在 prepare_context 之前短路。

证据边界
这是对当前源码排序 key 的直接推导；现有 test_lifecycle_phase.py 没有独立锁定“plugin 先于 built-in”的回归测试。不能把它描述成已经被测试证明的稳定公共合同。

真实插件：不要用虚构模块代替生产证据

证据 A：plugin_undo 插进 before_turn

class UndoCommandModule:
    slot = "plugin_undo.undo"
    requires = ("before_turn.acquire_session", "session:session")
    produces = ("session:ctx",)

class PluginUndo(Plugin):
    def before_turn_modules(self) -> list[object]:
        return [UndoCommandModule(self)]

它同时声明 acquire_session 这个 module 依赖和 session 这个 data 依赖，所以能确定地拿到 session，并在命令命中时提前产出 ctx。后续 built-in 会检测 session:ctx 已存在并跳过普通上下文准备。

证据 B：citation 展示两种影响方式

class CitationPromptModule:
    requires = ("prompt_render.emit", "prompt:ctx")
    produces = ("prompt:ctx",)
    # 直接修改 ctx.system_sections_bottom

class CitationAfterReasoningModule:

因此 export prefix 是宿主提供的结构化扩展约定，不是 Python 层面的强制沙箱。插件 module 仍可能直接修改 frame.slots 中的 ctx；真正的边界来自 phase 类型、slot 命名约定、collector 和测试。

失败边界：五种情况不要混在一起

情况当前行为为什么
Plugin module 依赖不存在的 module slot记录 warning，并递归禁用它及依赖它的 plugin module可选插件缺失不应破坏整条内置主链
Data slot 未闭合构造 Phase 时 warning，不自动禁用它是合同检查，不是拓扑边
Module slot 重复topo_sort_modules() 抛 RuntimeError节点身份必须唯一
Module 形成循环依赖RuntimeError("模块循环依赖...")不存在合法执行顺序
run() 异常 / 最终无 output异常向上传播 / Phase 抛错Phase 本身不做 failure isolation，也不允许静默返回空结果

最容易踩的坑：把“缺失插件依赖会禁用”误解为“所有错误都会 fail-open”。执行期异常仍然传播；插件 failure isolation 是另一层策略，不能从这里脑补出来。

七阶段只作迁移地图，不作本课背诵题

同一个 phase engine 还用于 before_reasoning、prompt_render、before_step、after_step、after_reasoning、after_turn。你本课只需知道：

  • Plugin base 为七个 phase 分别提供 *_modules() 扩展口。
  • PluginManager 分别收集，bootstrap 分别注入对应 runtime。
  • 各 phase 复用相同的 Frame / Module / topo sort / validate 模式，但拥有自己的输入、输出和 export 约定。

各 phase 的完整模块表应按需查源码，不要求在 Lesson 21 Part 1 一次记住。
