对应总计划 Lesson 10 Part 2

Amadeus 当前 Loop 对照精读与 Gap 标注

这节课不新增 runtime 功能，只把当前 Amadeus 已经做出来的 loop 主链讲成代码地图：哪几层已经对齐 Akashic，哪几层只是基础版，还不能误以为已经完全收口。

本课目标

  • 把当前 Amadeus 的 passive loop 主链按真实代码讲清
  • 明确 provider / runtime / tool_runtime / tests 各自职责
  • 标注当前已经对齐 Akashic 的点和还没收口的 gap

这节课结束后，你应该能回答：当前 Amadeus 为什么已经不是 single-shot，但又为什么还不能说“完全复现了 Akashic Reasoner.run()”。

先看整条代码主链

PassiveRuntime.run_turn()
-> SessionManager.get_or_create()
-> session.get_history()
-> ContextBuilder.render()
-> provider.chat(messages, tools)
-> response.tool_calls ?
   -> _run_tool_loop()
      -> append assistant(tool_calls)
      -> ToolExecutor.execute(...)
      -> append tool(result)
      -> provider.chat(...) again
   -> incomplete summary or final reply
-> parse_response()
-> session.add_message(user)
-> session.add_message(assistant, tool_chain?)
-> SessionManager.save()
-> TurnCommitted(extra={tool_chain})

对应关键位置： amadeus/runtime.py:49-127、 amadeus/runtime.py:129-258、 amadeus/provider.py:77-128、 amadeus/tool_runtime.py:21-58。

四个文件分别管什么

provider.py

负责“一次请求/响应”的 LLM 适配。它把 raw response 解析成 LLMResponse(content, tool_calls, ...)，但不管理循环本身。

关键看：amadeus/provider.py:77-128。

runtime.py

负责 turn 主控权和 multi-step loop。真正的“再调一次模型、再执行工具、到上限怎么办”都在这里。

关键看：amadeus/runtime.py:81-127 与 129-258。

tool_runtime.py

负责把协议消息拼回去：先 assistant tool call，再 tool result。它是 loop 的消息拼装辅助，不是 loop 控制器。

关键看：amadeus/tool_runtime.py:21-58。

test_runtime.py

负责证明当前行为已经到了哪一步。它是你判断“系统做到哪”最可靠的证据，不是可有可无的附属品。

关键看：tests/test_runtime.py:138-456。

按调用顺序精读当前实现

  1. 先取 session/history
    run_turn() 开头先做 get_or_create() 和 get_history()， 说明 loop 建立在已有会话边界之上，而不是每次请求都临时拼一个孤立 prompt。
  2. provider 返回结构化结果
    provider.chat() 不只返回文本，还可能返回 tool_calls。这里是 Lesson 8 的成果。
  3. 如果有 tool_calls，主控权交给 _run_tool_loop()
    关键在 amadeus/runtime.py:84-92。这就是“当前系统已经不是 single-shot”的决定性证据。
  4. loop 内部先 append assistant(tool_calls)
    append_assistant_tool_calls() 在执行工具前被调用，保证后续 tool_call_id 有协议来源。
  5. 执行每个工具并记录本轮结果
    ToolExecutor.execute(..., call_id, tool_batch, tool_batch_index) 已经把协议关联和批次信息传下去了。
  6. 把 tool result 回灌给下一轮 LLM
    append_tool_result() 把这次工具输出塞进 loop_messages，供下一轮 provider.chat() 继续推理。
  7. 到上限时返回阶段性 summary
    _render_incomplete_tool_loop_summary() 当前已经实现了“受控未完成态”，而不是直接抛异常。
  8. 最终只持久化 user / assistant，不持久化 tool 中间消息
    当前 session.add_message() 只写用户输入和最终 assistant 回复；tool_chain 挂在 assistant extra 上。

当前已经对齐 Akashic 的点

机制 当前状态
provider 输出 tool_calls 已对齐基础形状。当前可区分最终文本和工具调用请求。
assistant(tool_calls) -> tool(result) 协议顺序 已对齐，且有工具结果回灌下一轮 LLM。
多轮 tool loop 已对齐基础能力。当前测试已经覆盖连续两轮工具调用。
iteration limit 不崩溃 已对齐方向。当前会返回阶段性 summary，而不是直接报错。
tool_chain 持久化 已对齐观测面雏形。assistant extra 和 TurnCommitted.extra 都会带上它。
tool 中间消息不进入 session history 已对齐当前边界。测试明确验证 session 里只保留 user/assistant。

当前还没完全收口的 Gap

  • Loop 语义还是基础版
    当前有 while-loop、有 summary、有 trace，但还没有完整复现 Akashic 的 step phase、更加丰富的中断/继续语义和更完整的 metadata 组织。
  • tool_chain 还是轻量记录
    现在够做基础 trace 和持久化，但还没有达到 Akashic 那种更完整的观测信息密度。
  • session/history 边界虽然成形，但还要继续上课收口
    当前已经证明 tool 中间消息不进 history，但“哪些该进长期上下文、哪些只该留在 runtime 观测面”还要在 Lesson 11 继续打磨。
  • context-length / trim 还没接进 loop
    这就是 Lesson 12 要接的内容，否则 loop 遇到长上下文时还不够像 Akashic。

测试在这里不是补充品，而是阶段证据

  • tests/test_runtime.py:138-215：单轮 tool call 闭环
  • tests/test_runtime.py:218-307：多轮 tool loop 继续执行
  • tests/test_runtime.py:310-365：iteration limit 返回阶段性结果
  • tests/test_runtime.py:368-414：tool_chain 持久化进 assistant extra
  • tests/test_runtime.py:417-456：tool 中间消息不进入 session history

资深工程师判断“现在做到哪一步”，先看测试证明了什么，再看代码写了什么。因为代码能写得很像，行为却未必真的成立。

你现在应该能讲出的主链

  1. 为什么当前 Amadeus 已经不是 single-shot runtime
  2. provider 和 runtime 的职责边界
  3. tool_runtime.py 为什么是消息拼装辅助，不是 loop 控制器
  4. tool_chain 为什么是观测记录，不是执行编排器
  5. 当前已经对齐了哪些 Akashic 机制、还差哪些 gap
