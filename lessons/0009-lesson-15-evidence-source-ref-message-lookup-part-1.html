Lesson 15 Part 1

evidence / source_ref 回源链：从“像事实”到“能举证”

Lesson 14 解决的是：模型如何主动调用 recall_memory 拿到记忆摘要。 Lesson 15 解决的是：当摘要背后有 evidence 和 source_ref 时，系统如何回到原始 session message， 让最终回答不只是“看起来对”，而是有原文支撑。

一句人话

recall_memory 找线索，fetch_messages 拿原文。线索不是证据，原文才是证据。

Akashic 源码主链

主链不是“查数据库返回文本”，而是四段职责分离：

01recall result

返回 summary、id、source_ref、evidence。

02LLM 判断

发现答案需要具体原话或事实支撑。

03fetch_messages

传 evidence 或 source_ref，要求回源。

04SessionStore

按 message id 取原文，可带上下文窗口。

05final answer

基于原文回答，并按 citation rule 留标记。

sequenceDiagram
  participant LLM
  participant Recall as recall_memory
  participant Fetch as fetch_messages
  participant Store as SessionStore
  LLM->>Recall: recall_memory(query)
  Recall-->>LLM: items[{id, summary, source_ref, evidence}]
  LLM->>Fetch: fetch_messages(evidence/source_ref, context)
  Fetch->>Fetch: resolve ids from source_ref/evidence
  Fetch->>Store: fetch_by_ids / fetch_by_ids_with_context
  Store-->>Fetch: original session messages
  Fetch-->>LLM: messages[{id, role, content, in_source_ref}]
  LLM-->>LLM: answer with cited memory ids

源码精读：5 个关键点

        

          1. fetch_messages 是最终证据工具，不是检索工具
          

            Akashic 的描述写得很硬：recall_memory、search_messages、记忆注入都可能给线索，
            但能直接作为最终证据的是 fetch_messages 取回的原始消息。
          

        

        

          2. evidence 和 source_ref 都会进入同一个 ID 解析器
          

            _resolve_fetch_ids() 会合并 ids、source_ref、source_refs 和
            _source_refs_from_evidence() 的结果，再统一 _expand_source_ref()。
            这保证调用方不用关心自己拿到的是 evidence 还是 source_ref。
          

        

        

          3. #h:... 后缀不是 message id
          

            _expand_source_ref() 会先按 # 切开，只解析前半段。
            所以 ["tg:1:2","tg:1:3"]#profile 最终会变成 tg:1:2 和 tg:1:3。
          

        

        

          4. context 是为了还原上下文，不是扩大检索范围
          

            它只在已经命中的消息前后扩展窗口。命中消息会标记 in_source_ref=true，
            周边上下文只是帮助理解，不应该被误当作 source_ref 本身。
          

        

        

          5. preview 不能直接当证据
          

            SearchMessagesTool 是 grep 式定位工具，只给 preview 和 source_ref。
            一旦要用搜索结果回答事实，必须再调用 fetch_messages(source_ref) 拿原文。
          

        

        

          常见错误：把 recall summary 或 search preview 当成最终证据。正确做法是：summary/preview 只负责定位，最终事实要回源。
