本课目标与 MISSION.md 的关系

MISSION 要求你能从 Akashic 真实源码解释设计来源，再在 Amadeus 中亲手复现。本课完成后，你应能沿着 PassiveRuntime / RecallMemoryTool → MemoryQuery → VectorMemoryEngine → lanes → RRF → block/JSON 讲清输入、输出和失败边界。

  • 被动查询明确使用 intent=context。
  • 主动 answer 查询使用 raw query + event/general 两条 hypothesis。
  • procedure 查询生成多条变体，并对同 ID 结果 max-pool。
  • dense 与 lexical 各自排名后用确定性 RRF 融合。
  • 被动结果按类别和字符预算形成 context block；主动结果保持 tool JSON。

Part 2：Amadeus 复现练手

1. Query plan 按 intent 分流

_build_query_plan() 负责决定查询集合、kind 限制以及是否生成 hypothesis。调用方不再把所有检索都当成默认 answer。

context   → 当前消息或 context["queries"]
answer    → raw + event hypothesis + general hypothesis
procedure → raw + “执行…的步骤” + “…流程”，只查 procedure/preference

2. 两路排名与 RRF

_rank_rows() 分别产生 vector 和 lexical 排名，_rrf_merge() 使用 k=60、keyword_weight=0.5 融合名次。相同分数按 ID 稳定排序，避免测试和线上结果随机抖动。

rrf(id) = Σ lane_weight / (60 + rank_in_lane)

signals 同时保留 lanes、vector_score、lexical_score 和 rrf_score，不会再用一个 dominant lane 掩盖双路命中。

3. CJK lexical terms

_extract_terms() 保留英文词和数字，对较长中文片段生成 bigram，并过滤少量停用词。这里是 Akashic 风格的 OR-LIKE lexical lane，不宣称实现了标准 BM25。

4. 多查询 max-pool

每条查询复用同一套 lanes + RRF。同一个 memory ID 被多条 query 命中时，只保留最高融合分，并记录命中的 query index，避免主动 hypothesis 产生重复 JSON 条目。

5. 结构化注入

render_context_block() 按 Applicable Procedures、User Profile、Relevant History 分组。预算不足时丢弃完整低优先级条目，不截断成无法回源的半条记录；trace 记录 injected_ids、omitted_ids 和字符数。

真实数据流

被动线路

PassiveRuntime
  → MemoryQuery(intent="context", context={history, session_key})
  → dense + lexical → RRF
  → structured context block
  → RetrievedMemoryPromptBlock
  → context frame

主动线路

LLM tool_call(recall_memory)
  → MemoryQuery(intent="answer")
  → raw + event/general hypothesis
  → shared dense + lexical → RRF → max-pool
  → structured JSON
  → role=tool
  → 下一轮 LLM

两条线路可能看到同一 ID，但不做跨 message 去重：被动 block 是预先背景，主动 JSON 是模型带着具体意图查出的工具证据。事实冲突仍要通过 source_ref/evidence 回源。

实现中发现的真实 bug：主动 recall 死锁

原实现从正在运行的 event loop 内执行同步 tool，然后用 run_coroutine_threadsafe(..., same_loop).result() 等待同一个 loop。当前线程被 result() 阻塞后，loop 永远无法推进 query coroutine。

本课没有用 worker thread 绕过问题，因为 bootstrap 中的 hypothesis provider 与主 runtime 共享异步 LLM client，跨 event loop 使用仍可能失败。最终修复是让 ToolExecutor 增加原生 execute_async()：同步工具直接返回，异步工具由 runtime 在当前 loop 中 await。RecallMemoryTool.execute() 因而成为真正的 async tool。

验证步骤与当前证据

  1. 运行 focused：uv run --extra dev pytest tests/test_vector_memory.py tests/test_runtime_vector_memory.py -q。预期看到 RRF、hypothesis fail-open、预算、被动+主动同轮用例通过。
  2. 运行全量：uv run --extra dev pytest -q。当前证据：119 passed。
  3. 运行规范检查：uv run --extra dev ruff check amadeus tests。当前证据：All checks passed。
  4. 运行类型检查：uv run --extra dev mypy amadeus。当前证据：Success: no issues found in 31 source files。

联合测试会检查第一次 provider payload 已含被动 Relevant History，第二次 payload 仍保留它并新增一条 role=tool JSON。这证明两条线路不是用单元测试分别“假装存在”。

常见误区

  • 有类就等于已接入：错误。必须追实例化和调用位置。
  • RRF 融合相似度：错误。RRF 融合的是各 lane 名次。
  • 双路命中只留 dominant lane：会丢可解释性，应保留两路原始信号。
  • 主动和被动重叠就是冲突：重复 ID 只是不同阶段再次命中；冲突指两个事实内容不一致。
  • embedding 失败就没有检索：当前设计 fail-open 到 lexical lane。
