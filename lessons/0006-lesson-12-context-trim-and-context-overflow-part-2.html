对应总计划 Lesson 12 Part 2

Amadeus Context-Length Fallback 复现练手

这节课把 Part 1 讲过的 Akashic 机制落到 Amadeus：当 provider 抛出 ContextLengthError 时，runtime 不再直接失败，而是按 trim attempt 重新渲染 prompt、重试，并记录本轮用过的 fallback 计划。

本课目标

本课只复现 Akashic 的“应急预算控制链”，不把 compact / consolidation 混进来。也就是说，这节课解决的是： 

provider.chat(...)
-> ContextLengthError
-> build_context_trim_attempts(...)
-> disabled_sections + history_window
-> 重新 render prompt
-> retry
-> 成功后记录 context_retry
-> 全失败时返回可持久化 fallback reply

与 MISSION.md 的关系：这一步让 Amadeus 从“能跑 tool loop”进到“能在真实上下文压力下退化求生”，这是复杂 agent 架构里必须能讲清的能力。

Akashic 对应设计

  • ../../akashic-agent/agent/core/passive_turn.py：DefaultReasoner.run_turn() 持有 retry 主控权。
  • ../../akashic-agent/agent/prompting/budget.py：DEFAULT_CONTEXT_TRIM_PLANS 定义降载顺序。
  • ../../akashic-agent/agent/provider.py：provider 只把厂商错误归一成 ContextLengthError。

Amadeus 这次迁移的是核心数据流和生命周期边界：provider 仍然只识别错误；runtime 负责尝试不同 prompt 配置；prompt builder 继续只做渲染。

Amadeus 当前改动

文件 改动 职责
amadeus/runtime.py 引入 build_context_trim_attempts() 和 ContextLengthError 把已有预算计划接进被动 turn 主链
amadeus/runtime.py PassiveTurnResult 新增 context_retry 把 selected plan、trimmed sections、attempts 暴露给调用方和测试
amadeus/runtime.py run_turn() 外层加入 attempt loop 每次 retry 前重新构造 RuntimeContext 并重新 render prompt
amadeus/runtime.py 新增 _trim_session_history() 当后续 attempt 成功时，把 session raw history 收口到成功窗口
tests/test_runtime.py 新增两个 runtime 级测试 验证“超长后重试成功”和“全部失败后持久化 fallback reply”

关键代码精读

1. 生成 attempt 表

run_turn() 先用当前 model-facing history 的长度调用 build_context_trim_attempts(len(history))。这里得到的是一组配置，不是直接改 messages。

2. 每次重新 render

每个 attempt 都重新创建 RuntimeContext，传入 disabled_sections 和 history_window，再调用 context_builder.render()。

3. 捕获 provider 边界

只有 ContextLengthError 会进入下一轮 attempt。其他异常不吞掉，因为那不是上下文预算问题。

4. 成功后收口

成功后写入 selected_plan 和 trimmed_sections；如果不是第一个 attempt 成功，还会按成功窗口裁短 session history。

测试验证

本课新增的两个测试：

  • test_passive_runtime_retries_with_next_context_trim_attempt：第一次调用抛 ContextLengthError，第二次按 trim_runtime_metadata 重新 render 后成功。
  • test_passive_runtime_persists_fallback_when_all_context_trim_attempts_fail：所有 attempt 都超长时，runtime 持久化“上下文过长”回复，并保留 attempt trace。

当前还没复现的 Akashic 部分

  • Amadeus 还没有 Akashic 那套完整 observe 写入，把预算指标沉淀到独立 trace DB。
  • Amadeus 还没有完整 tool_search / preloaded tools 体系，所以 skills_catalog 类型的大块降载还只是 prompt block 级别。
  • runtime_metadata 是 Amadeus 当前的简化入口；Akashic 没有同名通用 prompt block，而是把 metadata 分流到 session_context、turn_injection_prompt、extra_hints、session metadata、event/outbound metadata 等链路。后续要拆成 LLM-visible 与 system-visible 两条链。
  • 当前 session trim 按成功窗口裁 raw messages，和 Akashic 一样是应急收口，不是 compact。

常见误区

  • 误以为 retry 是直接修改旧 messages。本课实现的是重新 render prompt。
  • 误以为 trim 是 compact。这里仍然是应急 fallback，不做无损压缩。
  • 误以为 provider 应该自己重试。provider 只识别错误，runtime 才知道 prompt 结构。
  • 误以为全失败应该抛异常。本课沿 Akashic 思路返回可持久化的 fallback reply，让 turn 生命周期闭合。

简历可讲述版本

我在 Amadeus 的被动 agent runtime 中复现了 Akashic 的 context-length fallback 机制：provider 只负责归一化上下文超长错误，runtime 根据 trim plan 逐级关闭低优先级 prompt block、缩小 history window 并重新渲染请求；成功后记录 retry trace，失败时返回可持久化的阶段性回复。这个设计把一次模型调用失败转成了可观测、可测试、可恢复的预算控制流程。

如果你自己重做一遍，第一步看什么

第一眼看 amadeus/runtime.py 的 run_turn()。确认它的主链是 session history、context render、provider call、tool loop、persist turn；然后把 retry 包在 provider call 和 tool loop 外层，而不是塞进 provider 或 prompt block。
