本课目标与 MISSION.md 的关系

MISSION 要求你能解释复杂 agent 为什么这样分层，而不是只会往主循环里加代码。Lifecycle 的价值是把“什么时候允许扩展、扩展能改什么、失败会影响谁”变成正式合同。

  • 按真实嵌套顺序复述 Akashic 七个 phase。
  • 根据控制流区分 Gate 与 Tap，而不是根据 before/after 名字猜。
  • 沿 module chain 讲清三个重点 phase 的输入、状态变化和输出。
  • 知道 Lesson 19 只复现哪三个 seam，以及为什么不提前迁移完整 plugin system。

Phase、Module、Frame、Context、Facade 各做什么

核心源码位于 agent/lifecycle/phase.py、types.py 和 facade.py。

第二层：Phase 只负责驱动 module chain

Akashic · agent/lifecycle/phase.py 打开完整文件 
class Phase(Generic[I, O, F]):
    def __init__(
        self,
        modules: Sequence[PhaseModule[F]],
        *,
        frame_factory: Callable[[I], F],
    ) -> None:
        self._modules = _disable_modules_with_missing_module_dependencies(modules)
        self._frame_factory = frame_factory
        self._validate()

    async def run(self, input: I) -> O:
        frame = self._frame_factory(input)
        for module in self._modules:
            frame = await module.run(frame)
        if frame.output is None:
            raise RuntimeError("Phase 模块链未产生 output")
        return frame.output
读法：
  1. PhaseFrame 保存 input、共享 slots 和最终 output。
  2. 每个 module 都接收同一个 frame，并把更新后的 frame 交给下一个 module。
  3. 没有任何插件 handler 时，这条内置 module chain 仍然可以完成整个阶段。

class TurnLifecycle:
    def __init__(self, bus: EventBus) -> None:
        self._bus = bus

    def on_before_turn(
        self,
        handler: Callable[
            [BeforeTurnCtx],
            Awaitable[BeforeTurnCtx | None] | BeforeTurnCtx | None,
        ],
    ) -> None:
        self._bus.on(BeforeTurnCtx, handler)

    def on_after_turn(
        self,
        handler: Callable[[AfterTurnCtx], Awaitable[None] | None],
    ) -> None:
        self._bus.on(AfterTurnCtx, handler)
最终分层：Phase 决定“这一阶段要完成哪些工作”；Module 决定“其中一个步骤怎么做”；Hook Point 决定“哪里允许扩展”；Handler 是“插件注册进来的具体函数”；Gate/Tap 决定“这些 handlers 有什么权限和失败语义”。

Gate 与 Tap：最重要的控制流区别

阅读 bus/event_bus.py 的 emit() 与 fanout()：

维度Gate event / emitTap event / fanout
目的干预后续执行观察已经形成的事实
顺序按注册顺序串行观察者并发
数据handler 可返回新 context，传给下一个 handler收到观察快照，不重写主结果
异常向调用链传播，不能带半修改状态继续单个观察者记录异常，其他观察者继续
典型公开事件before_turn、prompt_render、after_reasoningafter_step、after_turn
Gate:
ctx0 → handler A → ctx1 → handler B → ctx2 → 主链继续

Tap:
                         ┌→ observer A（失败，仅记录）
committed snapshot ──────┼→ observer B（正常）
                         └→ observer C（正常）
分类边界：这里的 Gate/Tap 描述公开 EventBus handler。Phase module chain 还有 slots 控制层；例如 after_step 的 observer 是 Tap，但 module 可以产出 step:early_stop_reason，让 Reasoner 安全收尾。不要把“fanout 是 Tap”误读成“整个 phase 永远不能影响控制流”。

Gate 怎么做：串行接收上一个 handler 的结果

Akashic · bus/event_bus.py · emit() 打开完整文件 
async def emit(self, event: E) -> E:
    for raw_handler in self._handlers.get(type(event), []):
        handler = cast(Handler[E], raw_handler)
        result = handler(event)
        if inspect.isawaitable(result):
            result = await result

        # handler 返回新 context 时，后一个 handler 会看到新值。
        if result is not None:
            event = cast(E, result)

    return event
为什么它是 interceptor pipeline：
  • handler A 修改后的 event 会继续传给 handler B。
  • 没有 try/except 隔离 handler；异常会离开 emit()，阻止主链使用半修改 context。
  • 调用方必须等待最终 context，才能进入下一步。

Tap 怎么做：并发观察，并把失败关在 observer 内

Akashic · bus/event_bus.py · fanout() 打开完整文件 
async def fanout(self, event: object) -> None:
    handlers = list(self._handlers.get(type(event), []))
    if not handlers:
        return

    results = await asyncio.gather(
        *(self._run_observer(event, handler) for handler in handlers)
    )
    failed_count = results.count(False)
    if failed_count:
        logger.warning(
            "fanout completed with observer errors: event=%s failed=%d total=%d",
            type(event).__name__,
            failed_count,
            len(handlers),
        )

async def _run_observer(self, event: object, handler: Handler[object]) -> bool:
    try:
        result = handler(event)
        if inspect.isawaitable(result):
            await result
        return True
    except Exception:
        logger.exception("observer error for %s", type(event).__name__)
        return False
为什么它是 observer fanout：
  • asyncio.gather() 同时启动 observers，而不是把 A 的输出传给 B。
  • 返回值只用于统计成功/失败，不会替换主流程中的 snapshot。
  • 每个 observer 自己捕获异常，所以一个监控模块损坏不会毁掉已形成的业务结果。

Tap 不等于“发生在整个操作之后”

“插件失败隔离”不能一概而论：Akashic 的 fanout observer 会隔离；PhaseModule 本身抛错仍可能传播。完整 plugin health/failure policy 留到 Lesson 23。

class _BuildBeforeTurnCtxModule:
    async def run(self, frame: BeforeTurnFrame) -> BeforeTurnFrame:
        state = frame.input
        bundle = cast(ContextBundle, frame.slots[_CONTEXT_BUNDLE_SLOT])
        frame.slots[_CTX_SLOT] = BeforeTurnCtx(
            session_key=state.session_key,
            channel=state.msg.channel,
            chat_id=state.msg.chat_id,
            content=state.msg.content,
            timestamp=state.msg.timestamp,
            skill_names=list(bundle.skill_mentions),
            retrieved_memory_block=bundle.retrieved_memory_block,
            retrieval_trace_raw=bundle.retrieval_trace_raw,
            history_messages=tuple(bundle.history_messages),
        )
        return frame

class _CollectBeforeTurnExportSlotsModule:
    async def run(self, frame: BeforeTurnFrame) -> BeforeTurnFrame:
        ctx = cast(BeforeTurnCtx, frame.slots[_CTX_SLOT])
        append_string_exports(
            ctx.extra_hints,
            collect_prefixed_slots(frame.slots, _EXTRA_HINT_PREFIX),
        )
        abort_reply = frame.slots.get(_ABORT_REPLY_SLOT)
        if isinstance(abort_reply, str) and abort_reply:
            ctx.abort = True
            ctx.abort_reply = abort_reply
        return frame
为什么先 build ctx 再开放 Hook：
  • handler 拿到的是稳定、收窄的 BeforeTurnCtx，不需要直接依赖整个 Runtime。
  • session、history、retrieval 和 skills 已经准备完成，handler 才有足够信息判断。
  • Gate 执行后，Phase 还会收集 plugin module 导出的 hints 与 abort slot，最后才返回 output。
阶段具体变化
acquire_session根据 session key 获取 session，并写回 TurnState.session
prepare_context读取 history、skill mentions、retrieved memory 与 retrieval trace
build_ctx把主链内部对象压缩为插件可理解的 typed context
emit插件按顺序修改 skills、hints、metadata，或设置 abort
collect_exports把 module slots 导出的 hints/abort reply 收回 context

为什么不是收到消息后立刻 emit？因为插件常需要 session、history 和 retrieval 状态才能判断。Akashic 先准备这些稳定输入，再开放 Gate。

abort：Akashic 可以设置 abort=True 和 abort_reply，让主链走 control outbound，不进入 reasoning。Amadeus Part 2 暂不迁 abort，因为当前 PassiveTurnResult 要求真实 message IDs，不能用空 ID 假装对齐。

    builtins = [
        _BuildPromptRenderCtxModule(),
        _EmitPromptRenderCtxModule(bus),

        _ReturnPromptRenderResultModule(),
    ]

class _EmitPromptRenderCtxModule:
    async def run(self, frame: PromptRenderFrame) -> PromptRenderFrame:
        ctx = cast(PromptRenderCtx, frame.slots[_CTX_SLOT])
        frame.slots[_CTX_SLOT] = await self._bus.emit(ctx)
        return frame

class _RenderPromptModule:
    async def run(self, frame: PromptRenderFrame) -> PromptRenderFrame:
        ctx = cast(PromptRenderCtx, frame.slots[_CTX_SLOT])
        rendered = self._context.render(
            ContextRequest(
                history=ctx.history,
                current_message=ctx.content,
                skill_names=ctx.skill_names,
                retrieved_memory_block=ctx.retrieved_memory_block,
                disabled_sections=ctx.disabled_sections,
                turn_injection_prompt=ctx.turn_injection_prompt,
            ),
            system_sections_top=ctx.system_sections_top,
            system_sections_bottom=ctx.system_sections_bottom,
        )
        messages = list(rendered.messages)
        if ctx.extra_hints:
            messages.append(build_context_hint_message(
                "plugin_hints", "\n".join(ctx.extra_hints)
            ))
        frame.slots[_RESULT_SLOT] = PromptRenderResult(messages=messages)
        return frame
沿数据流读：
  1. emit(ctx) 让 Gate handlers 修改 sections、hints 或 context 字段。
  2. CollectPromptExportSlots 把 plugin module 的 slot 输出合并回 ctx。
  3. 只有 ContextBuilder.render() 可以把这些结构化输入变成 provider messages，因此插件不会绕过预算、禁用 section 和 history 规则。

Gate 发生在真正渲染之前。插件能追加：

  • system_sections_top：高层系统段落。
  • system_sections_bottom：靠后的系统段落。
  • extra_hints：以受控 context hint 进入消息。

最终仍由 ContextBuilder.render() 统一处理 history、disabled sections 和 prompt assembly。插件不能绕开 builder 自己拼一份 messages，否则 trim/retry、预算和 system/context-frame 边界会失效。

与 Lesson 18 的 tool schema 区别：prompt-render 修改 messages；tool profile/schema 通过 provider 的 tools 参数进入模型。两条通道不能混写。

class _FanoutAfterTurnCtxModule:
    async def run(self, frame: AfterTurnFrame) -> AfterTurnFrame:
        ctx = cast(AfterTurnCtx, frame.slots[_CTX_SLOT])
        await self._bus.fanout(ctx)
        return frame

class _DispatchOutboundModule:
    async def run(self, frame: AfterTurnFrame) -> AfterTurnFrame:
        snap = frame.input
        outbound = snap.outbound
        if snap.state.dispatch_outbound:
            await self._outbound.dispatch(OutboundDispatch(
                channel=outbound.channel,
                chat_id=outbound.chat_id,
                content=outbound.content,
                thinking=outbound.thinking,
                metadata=outbound.metadata,
                media=outbound.media,
            ))
        return frame
这里要看顺序，而不只是类名：
  • TurnCommitted 先构造并 fanout，说明 reasoning 和持久化事实已经稳定。
  • AfterTurnCtx 再 fanout；observer 看到 will_dispatch，但不能修改 outbound。
  • DispatchOutboundModule 排在两个 Tap 后面，所以此时只能说“准备发送”，不能说“已经送达”。

AfterTurnCtx.will_dispatch 是“准备发送”的意图快照。handler 运行时真正 dispatch 还没有发生，因此 observer 可以记录发送前状态，但不能宣称消息已经成功送达。

时间点已经成立的事实尚未成立的事实
TurnCommitted fanoutreasoning 与持久化完成，commit payload 已构建outbound 未必已发送
AfterTurn fanout最终 reply/tool/telemetry 快照稳定dispatch 仍在后面
dispatch 后outbound port 已返回结果不属于当前 AfterTurnCtx 的观察时点

读测试时先问三件事：输入 context 是什么；handler 改了什么；最终由哪个生产调用点消费。只断言 handler 被调用，不足以证明 lifecycle 真正改变了主链。

常见误区与排错思路

  • 所有 after phase 都是观察者：错误。after_reasoning 能改最终输出，是 Gate。
  • EventBus 就是 plugin system：错误。它只负责执行 handler，不负责发现、配置、依赖和健康状态。
  • ToolHook 等于 lifecycle：错误。ToolHook 包围一次工具调用，turn lifecycle 包围整轮会话。
  • 插件可以直接拼 messages：会绕过 disabled sections、预算和 trim/retry，应把数据交回 prompt-render/context builder。
  • after_turn 表示已经发送：错误。Akashic 的 AfterTurn fanout 在 dispatch 前。
  • 所有插件异常都会被隔离：只有 observer fanout 明确隔离；Gate/module 错误可能传播。

资深工程师的排错顺序：先定位 phase 调用点，再看 typed context 的可写字段，然后看 handler 使用 emit 还是 fanout，最后追最终消费者或持久化变化。

Part 2：Amadeus 复现练手预告

通过复述门后，只复现三个 seam：

memory/history prepare
  → BeforeTurnContext → ordered Gate

RuntimeContext per retry attempt
  → PromptRenderContext → ordered Gate
  → ContextBuilder.render

persist + TurnCommitted
  → AfterTurnContext → isolated Tap
  → PassiveTurnResult

采用现有 EventBus + typed TurnLifecycle facade。Gate 异常传播，Tap observer 异常隔离。每次 prompt retry 创建新 context，避免上一次 handler 修改泄漏或重复累积。

Part 2 不实现 before-turn abort：Amadeus 当前结果类型要求 user/assistant message IDs。必须先设计统一 control-outbound/result contract，不能为了接口看起来相似而填空 ID。
