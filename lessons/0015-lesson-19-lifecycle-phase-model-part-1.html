本课目标与 MISSION.md 的关系

MISSION 要求你能解释复杂 agent 为什么这样分层，而不是只会往主循环里加代码。Lifecycle 的价值是把“什么时候允许扩展、扩展能改什么、失败会影响谁”变成正式合同。

  • 按真实嵌套顺序复述 Akashic 七个 phase。
  • 根据控制流区分 Gate 与 Tap，而不是根据 before/after 名字猜。
  • 沿 module chain 讲清三个重点 phase 的输入、状态变化和输出。
  • 知道 Lesson 19 只复现哪三个 seam，以及为什么不提前迁移完整 plugin system。

Part 1：Akashic 完整七阶段地图

先读 agent/core/passive_turn.py 文件头和 PassiveTurnPipeline.run()。真实结构不是七个平铺函数，其中三个 phase 位于 Reasoner 内部：

InboundMessage
└─ PassiveTurnPipeline
   ├─ 1. before_turn
   │     session acquire + ContextStore.prepare
   ├─ 2. before_reasoning
   │     tool context sync + prompt warmup
   ├─ Reasoner.run_turn
   │  ├─ 3. prompt_render
   │  │     ContextBuilder.render
   │  └─ reasoning loop
   │     ├─ 4. before_step
   │     ├─ provider response + tool execution
   │     └─ 5. after_step
   ├─ 6. after_reasoning
   │     reply modification + persist + outbound build
   └─ 7. after_turn
         TurnCommitted + observation + dispatch
Phase主要职责控制语义
before_turn准备 session/context，允许短路Gate
before_reasoning同步 tool context、skills、memory、prompt warmupGate
prompt_render追加 prompt sections/hints，再统一渲染Gate
before_step每轮 token estimate、hint、early stopGate
after_step观察当前轮 partial reply、tools、telemetryTap
after_reasoning修改最终 reply/media/metadata，持久化并构建 outboundGate
after_turn发布 commit/telemetry，最后 dispatchTap

关键校正：after_reasoning 虽然名字带 after，却仍然能改 reply 和 outbound，所以它是 Gate。分类依据是“能否改变后续事实”，不是名字。

Phase、Module、Frame、Context、Facade 各做什么

核心源码位于 agent/lifecycle/phase.py、types.py 和 facade.py。

对象职责不要误解成
Phase按已确定顺序运行 module chain，要求最终产生 output业务插件本身
PhaseModule完成一个小步骤，声明 slot/requires/produces整个 phase
PhaseFrame携带 input、共享 slots 和最终 output任意全局字典
Typed Context只暴露该 phase 合理拥有和修改的数据整个 AgentCore/Runtime
TurnLifecycle给插件提供稳定的 on_before_turn() 等注册入口具体执行引擎
EventBus执行有序 Gate 或隔离的观察者插件发现/加载器
Input
  → PhaseFrame(input, slots={}, output=None)
  → builtin module
  → plugin module
  → builtin finalize module
  → frame.output
  → Phase.run() 返回 output

slot/requires/produces 的深度实现属于 Lesson 21。本课只需知道：它让插件声明依赖而不是依赖手写注册顺序；缺失插件依赖会禁用相关模块，循环依赖会拒绝启动，数据 slot 未闭合会给出警告。

Gate 与 Tap：最重要的控制流区别

阅读 bus/event_bus.py 的 emit() 与 fanout()：

维度Gate / emitTap / fanout
目的干预后续执行观察已经形成的事实
顺序按注册顺序串行观察者并发
数据handler 可返回新 context，传给下一个 handler收到观察快照，不重写主结果
异常向调用链传播，不能带半修改状态继续单个观察者记录异常，其他观察者继续
典型 phasebefore_turn、prompt_render、after_reasoningafter_step、after_turn
Gate:
ctx0 → handler A → ctx1 → handler B → ctx2 → 主链继续

Tap:
                         ┌→ observer A（失败，仅记录）
committed snapshot ──────┼→ observer B（正常）
                         └→ observer C（正常）

“插件失败隔离”不能一概而论：Akashic 的 fanout observer 会隔离；PhaseModule 本身抛错仍可能传播。完整 plugin health/failure policy 留到 Lesson 23。

重点一：before_turn

源码：phases/before_turn.py。

TurnState
  → acquire_session
  → prepare_context
  → build_ctx
  → EventBus.emit(BeforeTurnCtx)
  → collect_exports
  → return BeforeTurnCtx
阶段具体变化
acquire_session根据 session key 获取 session，并写回 TurnState.session
prepare_context读取 history、skill mentions、retrieved memory 与 retrieval trace
build_ctx把主链内部对象压缩为插件可理解的 typed context
emit插件按顺序修改 skills、hints、metadata，或设置 abort
collect_exports把 module slots 导出的 hints/abort reply 收回 context

为什么不是收到消息后立刻 emit？因为插件常需要 session、history 和 retrieval 状态才能判断。Akashic 先准备这些稳定输入，再开放 Gate。

abort：Akashic 可以设置 abort=True 和 abort_reply，让主链走 control outbound，不进入 reasoning。Amadeus Part 2 暂不迁 abort，因为当前 PassiveTurnResult 要求真实 message IDs，不能用空 ID 假装对齐。

重点二：prompt_render

源码：phases/prompt_render.py。

PromptRenderInput
  → build PromptRenderCtx
  → EventBus.emit(PromptRenderCtx)
  → collect section/hint exports
  → ContextBuilder.render(...)
  → PromptRenderResult(messages)

Gate 发生在真正渲染之前。插件能追加：

  • system_sections_top：高层系统段落。
  • system_sections_bottom：靠后的系统段落。
  • extra_hints：以受控 context hint 进入消息。

最终仍由 ContextBuilder.render() 统一处理 history、disabled sections 和 prompt assembly。插件不能绕开 builder 自己拼一份 messages，否则 trim/retry、预算和 system/context-frame 边界会失效。

与 Lesson 18 的 tool schema 区别：prompt-render 修改 messages；tool profile/schema 通过 provider 的 tools 参数进入模型。两条通道不能混写。

重点三：after_turn

源码：phases/after_turn.py。进入它之前，after_reasoning 已经完成 user/assistant 持久化并构建 outbound。

TurnSnapshot
  → build budget/react/tool-chain work
  → collect turn extra exports
  → build TurnCommitted
  → fanout TurnCommitted
  → build AfterTurnCtx(will_dispatch=...)
  → collect telemetry
  → fanout AfterTurnCtx
  → dispatch outbound（如果允许）
  → return OutboundMessage

AfterTurnCtx.will_dispatch 是“准备发送”的意图快照。handler 运行时真正 dispatch 还没有发生，因此 observer 可以记录发送前状态，但不能宣称消息已经成功送达。

时间点已经成立的事实尚未成立的事实
TurnCommitted fanoutreasoning 与持久化完成，commit payload 已构建outbound 未必已发送
AfterTurn fanout最终 reply/tool/telemetry 快照稳定dispatch 仍在后面
dispatch 后outbound port 已返回结果不属于当前 AfterTurnCtx 的观察时点

读测试时先问三件事：输入 context 是什么；handler 改了什么；最终由哪个生产调用点消费。只断言 handler 被调用，不足以证明 lifecycle 真正改变了主链。

常见误区与排错思路

  • 所有 after phase 都是观察者：错误。after_reasoning 能改最终输出，是 Gate。
  • EventBus 就是 plugin system：错误。它只负责执行 handler，不负责发现、配置、依赖和健康状态。
  • ToolHook 等于 lifecycle：错误。ToolHook 包围一次工具调用，turn lifecycle 包围整轮会话。
  • 插件可以直接拼 messages：会绕过 disabled sections、预算和 trim/retry，应把数据交回 prompt-render/context builder。
  • after_turn 表示已经发送：错误。Akashic 的 AfterTurn fanout 在 dispatch 前。
  • 所有插件异常都会被隔离：只有 observer fanout 明确隔离；Gate/module 错误可能传播。

资深工程师的排错顺序：先定位 phase 调用点，再看 typed context 的可写字段，然后看 handler 使用 emit 还是 fanout，最后追最终消费者或持久化变化。

Part 2：Amadeus 复现练手预告

通过复述门后，只复现三个 seam：

memory/history prepare
  → BeforeTurnContext → ordered Gate

RuntimeContext per retry attempt
  → PromptRenderContext → ordered Gate
  → ContextBuilder.render

persist + TurnCommitted
  → AfterTurnContext → isolated Tap
  → PassiveTurnResult

采用现有 EventBus + typed TurnLifecycle facade。Gate 异常传播，Tap observer 异常隔离。每次 prompt retry 创建新 context，避免上一次 handler 修改泄漏或重复累积。

Part 2 不实现 before-turn abort：Amadeus 当前结果类型要求 user/assistant message IDs。必须先设计统一 control-outbound/result contract，不能为了接口看起来相似而填空 ID。
