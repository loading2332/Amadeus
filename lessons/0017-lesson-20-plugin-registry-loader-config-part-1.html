本课目标与 MISSION.md 的关系

MISSION 要求我们理解并复现 Akashic 的真实扩展机制，而不是在 Runtime 里硬编码更多 handler。本课要建立三个判断能力：

  • 区分 Registry、Loader/Manager、Config 和 PluginContext 的职责。
  • 沿一次真实加载讲清模块导入时发生的“装饰器注册”和“类注册”。
  • 判断一个插件何时才算 loaded，以及失败时哪些状态必须回滚。

做完以后应该看到：Part 2 中，一个位于插件目录的最小模块无需修改 PassiveRuntime，即可被发现、读取配置、实例化，并挂入 Lesson 19 的 Lifecycle seam。

一条完整加载链

这里可以借用数据库事务的思维：discover 只是列候选项；import 到 initialize 是准备和写入状态；加入 _loaded 才是 commit。问题在于 Akashic 当前回滚并不完全，后面会单独审计。

第一步：Discover 只建立候选描述，不导入

源码：agent/plugins/manager.py。

def discover(self) -> list[dict[str, str]]:
    mods: list[dict[str, str]] = []
    seen_names: set[str] = set()
    for directory in self._dirs:
        if not directory.is_dir():
            continue
        source = directory.name
        for child in sorted(directory.iterdir()):
            if not child.is_dir():
                continue
            main = child / "plugin.py"
            if not main.exists():
                continue
            if child.name in seen_names:
                logger.warning("插件名重复，跳过: %s (%s)", child.name, main)
                continue
            seen_names.add(child.name)
            mods.append({
                "name": child.name,
                "module_path": str(main),
                "import_path": f"akasic_plugin_{source}_{child.name}",
            })
    return mods

输入：按优先级排列的 plugin dirs。输出：name、文件路径、独立 import path。关键合同：目录顺序优先，目录内按名字排序；同名插件 first-wins。

为什么生成独立 import_path？后续 Registry 用 func.__module__ 和 cls.__module__ 把同一次导入产生的 metadata 与 class 对齐；同时避免所有入口都叫 plugin 而互相覆盖 sys.modules。

第二步：Import 为什么会“自动注册”

最小插件：tests/fixtures/plugins/hello/plugin.py。

class Hello(Plugin):
    name = "hello"
    version = "0.1.0"

    @on_before_turn()
    async def on_before(self, event):
        event.extra_metadata["hello_touched"] = True
        return event

Python 执行这个 class body 时发生两次注册，顺序不能颠倒：

  1. 方法定义完成后，@on_before_turn() 立即执行，把原始函数及其模块路径写入 handler registry。
  2. 整个 Hello class 创建完成时，父类 Plugin.__init_subclass__() 自动执行，把 class 按模块路径登记。
# decorators.py：记录 metadata，仍返回原函数
def _get_or_create_handler(func, event_type, handler_type, **kwargs):
    existing = plugin_registry._handlers.get_by_name(
        event_type, func.__name__, func.__module__
    )
    if existing:
        return existing
    metadata = PluginHandlerMetadata(
        kind=MetadataKind.LIFECYCLE,
        event_type=event_type,
        handler_type=handler_type,
        handler=func,
        handler_name=func.__name__,
        plugin_module_path=func.__module__,
        **kwargs,
    )
    plugin_registry._handlers.append(metadata)
    return metadata

# base.py：class 创建完成时登记 class
class Plugin(ABC):
    def __init_subclass__(cls, **kwargs: object) -> None:
        super().__init_subclass__(**kwargs)
        from agent.plugins.registry import plugin_registry
        plugin_registry.register_class(cls)
# manager.py：把 plugin.py 当成包入口执行
spec = importlib.util.spec_from_file_location(
    module_name,
    path,
    submodule_search_locations=[str(path.parent)],
)
module = importlib.util.module_from_spec(spec)
sys.modules[module_name] = module
spec.loader.exec_module(module)

重要：Registry 并没有主动分析 Python 文件。是 Loader 执行模块，模块执行产生注册副作用。插件代码也因此拥有普通 Python 代码的全部权限；这不是沙箱。

第四步：Bind、Initialize 与 loaded commit

plugin_registry.register_instance(import_path, instance)
self._bind_handlers(instance, import_path)
tool_names = self._register_tools(instance, import_path)
self._bind_tool_hooks(instance, import_path)

# ...收集其他 phase modules...

try:
    await instance.initialize()
except Exception:
    plugin_registry.remove_plugin(import_path)
    for tool_name in tool_names:
        self._tool_registry.unregister(tool_name)
    # 截断本次新增的 hooks/modules
    return

self._loaded.add(import_path)

_bind_handlers() 的关键动作，是把 metadata 中保存的未绑定函数变成绑定实例的 handler：

for metadata in plugin_registry.get_handlers_by_module_path(module_path):
    if metadata.kind != MetadataKind.LIFECYCLE:
        continue
    context_type = _EVENT_TYPE_MAP.get(metadata.event_type)
    if context_type is None:
        continue
    bound = functools.partial(metadata.handler, instance)
    self._event_bus.on(context_type, bound)

装饰器阶段保存的是 Hello.on_before(self, event)；绑定后 EventBus 得到的才是只需要 event 的 callable。Lesson 19 的 seam 到这里才真正拥有自动加载的 handler。

复杂点、信任边界与 Akashic 当前缺口

  • Import 是任意代码执行：plugin.py 顶层代码会直接运行。Plugin directory 必须被视为受信任代码来源。
  • 全局 Registry 会污染测试：Akashic 测试必须在每例前后手工清空 classes、instances 和 handlers。
  • “schema”没有验证：错误类型和未知键仍会进入 PluginConfig。
  • 初始化回滚并不完整：handler 在 initialize 前已注册到 EventBus，但失败分支没有从 EventBus 注销；失败插件可能留下可触发 handler。
  • 导入失败可能残留模块：模块在执行前写入 sys.modules，异常分支没有显式移除。
  • terminate 也未解绑 EventBus：Registry 被清空不等于 EventBus 中的 callable 消失。
  • Context 权限很宽：插件可接触 tool registry、session manager、memory engine；它是依赖容器，不是权限沙箱。

这些不是否定 Akashic，而是源码迁移必须经过判断的地方。Amadeus 应继承其职责分层和加载链，同时用测试补齐原实现未证明的原子性与清理边界。
