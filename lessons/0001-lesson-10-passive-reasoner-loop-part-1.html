Akashic Passive Reasoner 多步 Loop 源码课

这节课不写新功能，先把 Akashic 的多步 loop 主链讲透，再对照当前 Amadeus 已经复现到了哪里、还差什么收口。

这节课为什么现在上

你当前已经不在 Tool Runtime 阶段，而是在 Passive Agent Loop 阶段中段。当前 amadeus/runtime.py 已经有基础多步 tool loop 和对应测试，但还没有完全收口成 Akashic 的 Reasoner.run() 语义。如果现在不把主链讲清，后面继续补 plugin、 trim、eval 时就会反复返工。

先抓一句话：Akashic 的 provider 只负责“把模型响应解析成结构化结果”，真正掌控多步 tool loop 的是 Reasoner.run()。

messages
-> provider.chat(...)
-> response.tool_calls?

   -> execute each tool

   -> continue next LLM round
-> no tool_calls
   -> final assistant reply

1. 为什么 Reasoner.run() 持有 loop

因为 loop 不只是“再调一次模型”，还要同时维护 messages、tool batch、 iteration、hooks、可见工具、阶段性总结和最终 metadata。provider 只应该关心一次请求/响应的解析。

2. 为什么先 append assistant(tool_calls)

因为后面的 tool 消息必须引用一个已经存在的 tool_call_id。如果你不先把 assistant 的 tool 调用消息压进消息序列，协议上就没有可追溯的调用来源。

3. messages vs tool_chain

messages 是下一轮 LLM 继续推理用的上下文；tool_chain 是运行时观测面， 用来做 trace、持久化、eval、回放和解释“这一轮发生了什么”。

4. 为什么 request 要带 batch 信息

call_id 负责关联消息协议，tool_batch / tool_batch_index 负责回答“这次工具调用在本轮第几个、和谁同批”，这是 hook、审计和问题定位的基础。

Part 2：对照当前 Amadeus

当前 Amadeus 已经对齐到的部分：

  • amadeus/provider.py 已有 LLMToolCall 和 LLMResponse.tool_calls
  • amadeus/tool_runtime.py 已有 append_assistant_tool_calls() 与 append_tool_result()
  • amadeus/runtime.py 已有 _run_tool_loop()、max_tool_iterations、tool_chain
  • tests/test_runtime.py 已经验证单轮、多轮、上限 summary、tool_chain 持久化和 history 过滤

当前还只是“基础版”的地方：

  • 还没有完整复现 Akashic 的 Reasoner.run() 周边语义，例如 step phases、更加完整的 incomplete summary 策略
  • messages / tool_chain / session 持久化边界虽然已经成形，但还需要继续做 Lesson 11 收口
  • 后续 plugin、trim、eval 接入时，loop 还要继续验证是不是稳定扩展点

你最容易误解的点

  • 误以为 provider 管整个 agent loop。错，provider 只做一次请求/响应解析。
  • 误以为 tool 中间消息就应该进入用户长期历史。错，它们主要服务 runtime 继续推理，不等于用户真实对话历史。
  • 误以为达到 max_iterations 就应该直接抛错。Akashic 更像是返回“阶段性结果”，让系统可观测、可继续。

这节课你必须能复述的 5 个问题

  1. 为什么 Akashic 把多步 tool loop 放在 Reasoner.run()，而不是 provider？
  2. 为什么 assistant(tool_calls) 必须先于 tool(result)？
  3. messages 和 tool_chain 各自解决什么问题？
  4. 为什么 ToolExecutionRequest 需要 call_id / tool_batch / tool_batch_index？
  5. 为什么 max_iterations 更适合返回阶段性总结，而不是直接报错结束？
