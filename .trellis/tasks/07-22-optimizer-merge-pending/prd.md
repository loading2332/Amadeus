# 定期合并待处理记忆

## 目标

让已由对话归纳写入 `memory/PENDING.md` 的长期事实，在 Amadeus 进程持续运行时被定期整理进 `memory/MEMORY.md`，而无需人工调用 `MemoryOptimizer.optimize()`。

## 已确认事实

- `MarkdownMemoryMaintenance` 会把已确认的长期事实写入 `PENDING.md`；`MemoryOptimizer.optimize()` 已负责把其快照与现有 `MEMORY.md` 交给模型合并。
- 优化器在 `amadeus/memory/markdown.py` 中已有进程内互斥锁、快照提交、空模型输出回滚和异常回滚；不能绕开这些事务边界直接读写两个 Markdown 文件。
- `PassiveApp` 已有 `start()` / `aclose()` 生命周期，但目前没有后台任务会调用优化器。
- Akashic 的对应机制是可配置启用的后台循环，默认间隔为 64,800 秒（18 小时）。该实现只是可迁移的生命周期与配置契约，不复制其目录结构。
- 当前 FastAPI Web 进程只创建/查询 turn，不构造 `PassiveApp`；实际运行记忆与模型的是 `TurnWorker`。因此周期任务应由 `PassiveApp` 托管，网页被访问、关闭或刷新均不影响其计时。

## 需求

- R1：应用启动后，在独立的异步后台循环中按固定周期调用已有的 `MemoryOptimizer.optimize()`。
- R2：应用关闭时应停止并等待该后台循环，不能遗留任务或在资源关闭后继续调用模型。
- R3：每次触发必须复用优化器现有的快照、提交和回滚语义；执行重叠时不得并发合并同一份待处理记忆。
- R4：启用状态和周期必须可由运行时配置控制，并提供安全、可预测的默认值。
- R5：失败不得清空 `PENDING.md`，后台任务必须记录失败并继续等待下一个周期。
- R6：默认启用，默认周期为 64,800 秒（18 小时）；周期按墙上时钟的下一个 18 小时边界对齐，而不是从 Docker/worker 启动时开始完整计时。重启只重新计算下一个边界，不补跑错过的周期。

## 验收标准

- [ ] 在可控的短周期测试中，写入 `PENDING.md` 后，后台循环会调用优化器并更新 `MEMORY.md`。
- [ ] 配置可禁用该循环；禁用时不会创建后台任务或触发模型调用。
- [ ] 应用关闭会取消并等待后台循环；关闭后不再触发新的优化。
- [ ] 优化器失败或返回空内容时，`PENDING.md` 仍保留待合并事实，之后的周期仍可继续执行。
- [ ] 覆盖配置解析、应用生命周期和失败恢复的自动化测试通过。

## 暂不包含

- Dashboard 手动触发、状态 API、跨多进程/多实例分布式锁。
- 改变 `MemoryOptimizer` 生成的提示词、合并规则或 Markdown 文件格式。
