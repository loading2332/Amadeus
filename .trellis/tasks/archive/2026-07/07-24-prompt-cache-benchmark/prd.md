# 建立 Prompt Cache 可复现实验

## 目标与用户价值

建立一套可重复运行的 Prompt Cache 基准实验，使开发者能以请求返回的用量字段、端到端延迟和统一的成本模型，量化缓存命中相对于未命中的改善幅度，而不是凭提示词的表面相似性判断。

## 已确认事实

- Amadeus 通过 OpenAI Python SDK 的 Chat Completions 兼容接口调用模型；运行时可由 `OPENAI_BASE_URL` 与 `OPENAI_MODEL` 指定实际供应商和模型。
- 当前代码会将供应商返回的 `usage` 原样保留在 `LLMResponse.usage`，但未实现 Prompt Cache 指标采集或报告。
- 本地环境已配置运行时端点与模型；不在任务文档中记录密钥或其他敏感配置。
- 官方资料显示，缓存优化的共同前提是：满足模型的最小输入阈值、在缓存存活窗口内复用完全相同的前缀，并把每次请求变化的内容放在这个前缀之后。不同供应商的阈值、路由和显式控制 API 不同。
- OpenAI 的 Chat Completions 响应可在 `usage.prompt_tokens_details.cached_tokens` 返回读取 token；较新模型还会返回 `cache_write_tokens`。OpenAI 将 1,024 token 作为自动缓存的通常起点，并建议复用 `prompt_cache_key` 来改善拥有共享长前缀的请求的路由一致性。
- Anthropic 以 `cache_read_input_tokens` 与 `cache_creation_input_tokens` 区分读取和写入；缓存断点之前的全部内容必须完全一致，变化的时间戳、工具定义、图片或推理参数可能破坏复用。
- Gemini 报告 `usage.total_cached_tokens`；当前文档列出的隐式缓存最低输入阈值因模型而异（2,048 或 4,096），并同样要求把大型公共内容置于前部、在短时间内发送相近前缀。
- DeepSeek API 默认启用上下文硬盘缓存，并在 `usage` 中直接返回 `prompt_cache_hit_tokens` 和 `prompt_cache_miss_tokens`。缓存为尽力而为，构建需秒级，闲置后通常在数小时至数天内清除。
- DeepSeek 的命中对象是已落盘的“缓存前缀单元”，后续请求必须完整匹配该单元。单次长文本请求的后缀改变不保证第二次就命中；供应商可能在多次公共前缀观察后才将该公共前缀作为独立单元落盘。因此实验必须单列预热与测量阶段。
- Amadeus 现有 `MessageEnvelopeBuilder` 已按“系统提示词 → 历史 → 动态 context frame（近期上下文、检索记忆、运行时元数据）→ 当前用户消息”组装请求。因此 B 应复刻现有生产排列；A 仅作为故意将动态数据置前的反事实基线，不代表建议上线的实现。

## 需求

- 设计真实 API 实验，而非用 mock 估算缓存收益。
- 采用 A/B 实验比较两种提示词构造：A 为预期低缓存复用的对照，B 为预期高缓存复用的方案。
- 对照组与实验组必须只在预期影响缓存命中的输入结构上不同，并保持模型、生成参数、输出长度目标和并发条件一致。
- 报告必须能区分供应商显式返回的缓存 token 与无法直接观测的情况，不能把延迟下降误报为缓存命中。
- 结果应包含足以解释成本、首 token 延迟与总耗时差异的原始观测与汇总统计。
- 实验必须能在 Amadeus 当前 OpenAI 兼容配置下运行；若端点不返回标准缓存字段，应给出诚实的降级结论。

## A/B 场景定义

两组使用相同模型、相同生成参数、相同静态指令/工具定义/记忆材料、相同用户问题集、相同请求数和串行节奏。每个请求使用唯一 `request_id`，以保证动态部分确实变化。

- **A：动态前缀（基线/低复用）**。将 `request_id`、当前轮用户问题与本轮检索记忆等动态内容放在请求开头，再附上完全相同的静态 Agent 上下文。由于每次请求从第一个 token 起即不同，DeepSeek 不应能复用有意义的公共前缀单元。
- **B：稳定前缀（候选优化/高复用）**。先放完全相同的静态 Agent 上下文（系统指令、固定工具定义、固定示例、固定知识/记忆 fixture），再放 `request_id`、当前轮用户问题与本轮检索记忆。请求从开头到静态上下文末尾完全相同，随后仅后缀不同，因而具备复用已落盘缓存前缀单元的条件。
- **预热不计入 A/B**。每组先发送足量相同结构的预热请求，等待 DeepSeek 完成缓存构建与公共前缀检测；只有后续测量请求进入统计。预热次数、间隔与每个请求的原始用量均需记录。

默认实验规模为每组 3 次预热请求与 30 次串行测量请求。串行发送用于降低并发路由和缓存构建时序造成的混杂；报告必须保留每次请求的开始与结束时间，以便识别异常波动。

单次真实运行的预算上限为 5 美元等值。脚本须依据 DeepSeek 返回的 hit/miss/input/output token 与显式传入的单价累计估算成本；预估累计成本达到上限即停止后续请求，并将结果标记为预算截断。

该对照只检验“将动态内容移至稳定前缀之后”对缓存读取的影响；它不主张 A 完全没有任何缓存，也不把 B 的缓存读取视为必然发生。

实现时 B 必须严格沿用生产消息信封的顺序；A 只在 benchmark fixture 内重排，不修改生产 `MessageEnvelopeBuilder`。

第一版只执行 A/B 两组，不加入人为扩长稳定上下文的 B+ 收益上限实验。B 的结论仅代表当前生产结构及其 fixture 尺寸。

## 首次运行证据与下一轮范围

- 首次运行（`prompt-cache-20260724T074654Z-37e5b5`）中，A 的请求命中率与 token 缓存读取率均为 0；B 的请求命中率为 100%，但 token 缓存读取率为 94.94%，即每次约 2,944 token 命中、约 157 token 未命中。
- 该结果证明了稳定前缀排序对缓存读取的因果作用，但 A 是刻意破坏前缀的教学型下界，不能代表生产优化的增幅。
- 下一轮应以 B0（当前生产 prompt 结构）和 B1（一个具体且语义等价的生产优化候选）比较；只有 B0/B1 的差值才作为“可上线优化带来的缓存提升”。

## 第二轮运行证据（2026-07-26）

- 无历史 fixture 的首次 b0b1 运行（`prompt-cache-20260726T081836Z-081868`）：B0/B1 读取率完全相同（93.68%），实证 DeepSeek 缓存按字节前缀匹配、对 system/user 角色边界不敏感；无历史时两种排列字节等价，测不出差异。该运行保留为机理证据。
- 补入 15 轮（约 3.5k token）固定历史后的正式运行（`prompt-cache-20260726T082711Z-174045`，K=5，每组 3 预热 + 30 测量，全部可直接观测）：
  - Token 缓存读取率：B0 91.33% → B1 94.73%（+3.40pp）。
  - 每次记忆变更的稳态 miss：B0 ≈3,823 token（记忆+历史+frame 全部重处理）→ B1 ≈1,262 token（仅记忆+frame），−67%。
  - 平均每请求输入成本（示例单价 hit $0.0028/M、miss $0.14/M）：B0 $0.000124 → B1 $0.0000846，**−31.7%**。
  - 稳态请求两组均只 miss 约 110–115 token；差异全部来自记忆变更时点，与机理预测一致。
  - B1 首次记忆变更 miss 5,487 token 高于后续稳态，符合“缓存前缀单元需观察后落盘”的 DeepSeek 行为；诚实保留，不剔除。
- 结论边界：数字只对 K=5、该历史规模与 fixture 尺寸成立；记忆更新越频繁、历史越长，B1 优势越大；两组总耗时中位数差异在噪声内，不主张延迟改善。

## B0/B1 场景定义（第二轮）

第一轮 B 组使用固定不变的记忆 fixture，因此优化前的生产结构也能达到高读取率；B0/B1 的差异只有在“长期记忆在请求之间更新”的真实负载下才会显现。第二轮在两组间引入完全相同的记忆变更计划：

- **B0：优化前生产结构**。system prompt 按旧版 `PromptAssembler` 路由，包含 identity、`self_model` 与 `long_term_memory`；其后为固定多轮对话历史，再到动态 context frame 与当前用户消息。记忆更新会改变 system prompt 内容，即从记忆位置起破坏前缀，**其后的整段历史 token 全部变为 miss**。
- **B1：优化后生产结构**。system prompt 仅含 identity 等真正稳定的部分；`self_model` 与 `long_term_memory` 移入历史之后的动态 context frame（对应 `assembler.py` 中 `CONTEXT_FRAME_SECTIONS` 加入这两个 section 的改动）。记忆更新只影响末尾小段，identity 与历史构成的长前缀保持字节级稳定。
- **两组共享相同的固定多轮历史 fixture**（数千 token 规模）。历史是对照的关键：2026-07-26 的无历史 b0b1 运行（`prompt-cache-20260726T081836Z-081868`）中两组读取率完全相同（93.68%），实证 DeepSeek 缓存按字节前缀匹配、对 system/user 角色边界不敏感；无历史时 B0/B1 排列字节等价，测不出差异。
- **记忆变更负载**：每 K 次测量请求更新一次 `long_term_memory` fixture 内容（默认 K=5），模拟 Amadeus 记忆抽取/优化的真实写入节奏。两组使用相同的变更时点与相同的记忆内容序列；K 须记录在报告中，结论只对该变更频率与该历史规模成立。
- 两组仍使用相同模型、相同生成参数、相同问题多重集、相同预热与串行节奏；B0/B1 请求由 benchmark fixture 忠实复刻两种排列，不在实验中直接调用生产装配器。
- 主指标不变；简历口径的数字为 B1 相对 B0 的 token 缓存读取率提升，及按 DeepSeek 单价换算的输入成本降幅。

## 初步验收标准

- [x] 可通过单一命令对指定端点和模型运行预热、对照与命中实验，并输出机器可读原始记录。
- [x] 报告展示每组请求数、输入/输出 token、显式缓存 token、首 token 延迟（若流式可得）、总耗时及分位数/中位数。
- [x] 报告明确列出供应商是否实际返回缓存计量；缺失时标记为“不可直接证实”，而非声称命中。
- [x] 有自动化测试验证实验请求的固定前缀、变量隔离与统计计算，不调用真实 API。
- [x] 提供面向使用者的中文说明：缓存的工作前提、如何阅读实验结果，以及哪些结论不能从单次实验推出。
- [x] 报告包含 A/B 的精确定义、预热记录，并以 DeepSeek 返回的 `prompt_cache_hit_tokens`、`prompt_cache_miss_tokens` 计算主指标，不以预期替代观测。
- [x] B0/B1 实验在相同记忆变更负载下运行，报告给出 B1 相对 B0 的缓存读取率提升与估算输入成本降幅，并注明记忆变更频率 K。
- [x] `assembler.py` 的 section 路由改动有实验数据支撑，prompting 相关测试全部通过。

## 范围外

- 除 `PromptAssembler` 的 section 路由调整（`self_model`、`long_term_memory` 移入 context frame，即 B1 候选）外，不改变其他生产提示词内容或运行时默认模型策略；该调整须由 B0/B1 实验数据支撑后随本任务一并提交。
- 不将某个供应商的计费价格硬编码为普适事实；价格需要按实际供应商与时间单独配置或引用。

## 已定实验决策

- 主判据为：`sum(prompt_cache_hit_tokens) / sum(prompt_cache_hit_tokens + prompt_cache_miss_tokens)`；请求命中率与成本/延迟为辅助指标。
- 第一目标供应商为 DeepSeek API，负载为基于当前生产消息信封构造的脱敏固定 fixture。
